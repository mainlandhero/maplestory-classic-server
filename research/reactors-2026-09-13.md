## 1. Finding the pool from its data

No prior note in this repo touched reactors. The client's format strings `Reactor/%07d.img`,
`Reactor/%s.img` and `Sound/Reactor.img/%s/%s` are read through `.data` pointer slots
(`0x143a47158`, `0x143a47150`, `0x143a47148`; `tools/dataref.py`) by `FUN_141f45880` and
`FUN_141f47130` - the template loaders. `tools/callers.py` up two levels from either reaches
`FUN_141f2c0a0`, whose single caller is `FUN_141820080` = `CField::OnPacket`, at
`0x141821f5a`. **[L]** That is the reactor pool's packet dispatcher.

Its head **[L]**:

```text
141f2c0be  add  edx, 0xfffffb88      ; opcode - 0x478
141f2c0c4  cmp  edx, 0x14 ; ja default
141f2c0d0  lea  rcx, [imagebase]
141f2c0d7  mov  edx, [rcx + rax*4 + 0x1f2c3e4] ; jmp   21-entry table
```

Decoding the table (`python`, image-relative dwords at `0x141f2c3e4`):

| opcode | handler | reads (`tools/reads.py <fn> 2`) | name |
|---|---|---|---|
| `0x0478` | `FUN_141f2c440` | u32, u8, u16, u16, u16, u8, u32, u32 | ChangeState |
| `0x0484` | `FUN_141f2d9c0` | u8, u32, u32, u8, u16, u16, u8, str | EnterField |
| `0x0485` | `FUN_141f2d7f0` | u32 | LeaveField |
| `0x0487` | `FUN_141f2f8f0` | - | (not sent) |
| `0x0489` | `FUN_141f2fb90` | - | (not sent) |
| `0x048C` | `FUN_141f2ef50` | u32, u8, u8, u16, u16, u8 | (not sent) |
| others | the default arm | | |

The reference server's `ReactorPool.java` encodes `reactorEnterField` as `byte 0, int
objectId, int templateId, byte state, position, byte flip, string name` and
`reactorChangeState` as `int objectId, byte state, position, short delay, byte eventIdx, int
stateLength, int ownerId` **[R]** - the same widths in the same order as the reads above, which
is as good as a reference reading gets here. `crates/net/src/reactor.rs` builds exactly those.

## 2. The hit, outbound

`research/msexe-send-opcodes.txt` filtered to builders in the pool's code range
(`0x141f2....0x141f4....`): `0x032F` from five sites, `0x0330..0x0336`, `0x0351`.
`research/msexe-packet-fields.txt` gives `FUN_141f30aa0` (0x032F) the encode order
`u32, u32, FUN_1406ed940 (a 2-byte write), u32` - the classic `ReactorHit`: object id, hit
option, delay, skill id. `FUN_141f31630` (0x0330, `u32 ...`) is the touch. **[I]** until a
capture; the world server names both and logs the body of either.

## 3. The Wooden Box

`Reactor.wz/0000001.img` **[L]**: `info/info wooden box`; states `0..3` each carry
`event/0 {type 0, state N+1}` and a `hit` animation; state `4` has neither - broken. Four hits.
`action q90008` is the script the real server ran on break (the drops); ours is a table.

Placements are `Map.wz/<map>.img/reactor/<n>`: `id`, `x`, `y`, `reactorTime` (seconds; 120
everywhere but three boxes on map 1000 at 180, 90), `f`, `name` (empty). The six Amherst maps
carry 5 + 6 + 2 + 2 + 1 + 3 = **19**, which is the fan site's count exactly. **[L]**

`tools/dump_portals.py` now writes `gm-handbook/reactors.txt` for every map (228 rows, nine
reactor images) with `breakAt` = the number of states carrying an `event`, read from
`Reactor.wz`. Both packagers require the file.

## 4. Drops

`https://meowdb.com/msclassic/api/breakable-drops?breakableId=0000001` (the page loads it
client-side; the id is the seven-digit string): Old Wooden Board 4031004, Rusty Screw
4031003, Apple 2010001, Egg 2010002, all community-confirmed. `0000003`: Plant Sample
**4031072**; `0000004`: Witchgrass Leaf **4031012**; `0000005..7`: Coconut **4000061**;
`0000002`, `8`, `9`: nothing. (The site's own `itemId` column is its row id - 408, 510, 450 -
not a game id; `itemIconKey` is the game id.) `data/reactor-drops.txt` carries them in
`drops.txt`'s shape; the chances are ours. The quest items pass `crate::questitems::filter_roll`
with the breaker as the audience, per the owner: *"if it is a Quest Item, normal quest item drop
rules applies"*.

## 5. What the server does

`crate::fields`: every placement is seeded standing (state 0) on first entry, object ids
6000.. per map; a hit advances the state; the hit that reaches `breakAt` removes it and
schedules it back `reactorTime` later. `crate::session::reactor`: `0x0484` per standing
reactor on field entry (after the NPCs); `0x032F` -> `0x0478` to everyone on the map, and on
the break the rolled drops land at the box the way a mob's land at the corpse; the tick sends
`0x0485` + `0x0484` for each respawn. Unverified on screen; plan step TO(n).

## 6. Not established

* That `0x032F` is the hit (section 2). The first swing at a box settles it.
* What the client does with `delay` and `stateLength` on screen; the delay is echoed from
  the client's own packet and the length sent 0, as the reference does.
* Whether `0x0485` before `0x0484` on the same id is what the client wants for a respawn,
  or whether re-sending `0x0484` alone re-initialises it (the mob pool does that for a known
  id; the reactor pool has not been read for it).
