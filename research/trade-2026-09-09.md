# Player-to-player trade: the miniroom protocol

2026-09-09. Static, from `client-patched/MapleStory.exe` (base `0x140000000`), plus two
archived captures. No Ghidra, no client run, no code written.

Claims are tagged **[L]** read off this client's listing / string table / a capture,
**[D]** derived from tagged facts, **[I]** inferred.

**Headline:** trade is not its own protocol. It is one *kind* of miniroom, and the whole
family rides on outbound `0x017E` and inbound `0x0575`. The invite flow is **two** outbound
packets, not one - a create and then an invite. And the inbound invite has a hard gate: the
type field must be **1** or **2** or the client builds no popup at all and returns silently.

---

## 0. Instruments, and one of them was wrong

Positive controls run before anything was believed:

* `python tools/reads.py 0x140304100 2` - passes (mixed direct + helper reads). [L]
* `python tools/encodes.py 0x141cb6880 1` - passes (`0x2ff` ctor at `141cb7eb1`). [L]
* `tools/dump_stringids.py` decrypts ids to sensible English. [L]

**`tools/encodes.py`'s `SEND` label is wrong, and it cost me a wrong conclusion.** It maps
`0x1406ED610` to `SEND`. `0x1406ED610` is the **destructor** - it frees the two sub-objects
at `pkt+0x438` and `pkt+0x408` and does nothing else: [L]

```
1406ed610  push rbx / sub rsp,0x20 / mov rbx,rcx
1406ed619  add  rcx, 0x438        ; call 1406f19d0
1406ed626  lea  rcx, [rbx + 0x408] ; jmp 1406f1a40
```

The real send is **`0x1415D01C0`**: it fetches a singleton (`140caa510`), does per-opcode
bookkeeping keyed on `pkt+0x434` (the opcode), then `140caa4d0` -> `1415d3990(socket, pkt)`. [L]

`encodes.py` is also blind to **`0x1406EE160` = `COutPacket::Init(opcode)`** - it rewrites
`pkt+0x434`, zeroes the cursor and `pkt+0x428`, and re-emits the u16 opcode, so one stack
buffer can carry several packets in sequence. [L]

Together those two gaps made me read `FUN_141826bc0` as building a decoy body and throwing
it away. **The capture says both bodies go on the wire** (section 2). This is the
`CLAUDE.md` rule again: the screen - here, the log - wins over the static reading. Anything
in `research/` that counted packets with `encodes.py`'s `SEND` marker is suspect.

**Deduplication.** `previous-runs/world-20260904-192942.log` and
`research/fixtures/first-party-drawn-level-zero-and-three-refusals-world.log` are
byte-identical (`md5 32a92844c8c811daa025449a9d5733c1`, 3 930 784 B). That is **one**
observation under two names, not two. A third file,
`research/fixtures/sweep-0024-01c3-reply-0171.log`, contains `>>> opcode 0x017E +32B` - that
is a synthetic opcode sweep walking `0x017A, 0x017B, 0x017C, ...`, **not** a trade packet.
Do not count it.

## 1. Outbound: `0x017E`, `u32 mode` first, then a per-mode body

### 1.1 The enumeration

Every `mov edx, 0x17E` in `.text` was found by byte scan and then **re-decoded with a real
disassembler at each hit** (a byte scan alone is the antipattern `reads.py`'s docstring
warns about; it is used here only to generate candidates). 59 candidates; **51 immediately
precede `COutPacket::COutPacket` (`1406ED520`), 1 precedes `Init` (`1406EE160`), 7 are
unrelated**. [L]

Every one of the 52 writes the mode as a **4-byte `w_raw`**, not a `w_u32` - same bytes on
the wire, but it means a scan for `w_u32` after the ctor finds nothing.

### 1.2 The trade invite is TWO packets

`FUN_141826bc0(this, pUser, actionIndex, ...)` is the click handler behind the player
context menu. `actionIndex` (in `edi`) forks at `141826d0a`: [L]

* `actionIndex == 1` -> `141826e30`, the `0x017E` block below.
* `actionIndex == 2` -> `141826de6`, an entirely **different opcode**, `0x02F8`.

The `0x02F8` branch is the one gated by *"Lv. 60 or below characters cannot trade cash
items."* (`0x11F5`) and *"Characters created less than 3 days ago cannot trade cash items."*
(`0x11F6`), and both branches sit under *"Due to your country's local regulations, 1:1
trades, player shop are unavailable."* (`0x174E`). So `actionIndex` 1 = **trade**, 2 = **cash
trade**. [D]

The `actionIndex == 1` block is straight-line - no branch target between `141826e30` and
`141826ef7` - and builds **two packets in one stack buffer**: [L]

```
141826e40  mov edx,0x17E ; COutPacket ctor
141826e50    w_raw 4 <- 0            ; mode  = 0
141826e6d    w_raw 4 <- 1            ; roomType = 1
141826e8a    w_u8    <- 0
141826e96  call 1415d01c0            ; SEND  (9 bytes)
141826ea0  mov edx,0x17E ; COutPacket::Init  -- same buffer, reset
141826eaf    w_raw 4 <- 5            ; mode  = 5
141826ecc    w_u32   <- FUN_14276df20(pUser)
141826ee0  call 1415d01c0            ; SEND  (8 bytes)
141826ef0  call 1406ed610            ; dtor
```

`FUN_14276df20` is one instruction: `mov eax, [rcx + 0x10d0]`. [L]

**Wire form, both measured against a capture:**

| | opcode | body | bytes |
|---|---|---|---|
| create | `0x017E` | `u32 mode=0`, `u32 roomType=1`, `u8 0` | **9** |
| invite | `0x017E` | `u32 mode=5`, `u32 targetCharacterId` | **8** |

The 2026-09-04 capture, 9 ms apart, in that order: [L]

```
23:28:29.709 <- 0x017E UNKNOWN, 9 byte body 000000000100000000
23:28:29.718 <- 0x017E UNKNOWN, 8 byte body 05000000d6000000
```

`0xD6` = 214 = the target character's id, which is also what proves `user+0x10d0` is the
character id. The invite quoted in the brief (`05000000d5000000`, target 213) is a
**separate run**; only one line of it was quoted, so whether it too was preceded by a mode-0
create is not established here - but `FUN_141826bc0` has no path that sends the invite
without the create first, so it must have been. [D]

**The server must expect the create before the invite.** A server that answers only mode 5
is answering the second half of a two-packet handshake.

Cash trade (`actionIndex == 2`) is `0x02F8` with body `u8 0`, `u32 targetCharacterId` = **5
bytes** (`141826de6`..`141826e26`). [L] Not captured; not decoded further here.

### 1.3 Answering an invite

`FUN_141c3d820(ecx = ticket, edx = reason)` builds both replies, one per branch: [L]

| | opcode | body | bytes |
|---|---|---|---|
| accept | `0x017E` | `u32 mode=3`, `u32 ticket`, `u8 0`, `u8 0` | **10** |
| decline | `0x017E` | `u32 mode=6`, `u32 ticket`, `u32 reason` | **12** |

`edx == 0` takes the accept branch. The client auto-declines with `reason = 4` normally and
`reason = 0xB` when a miniroom is already open (`141c3e178`). [L]

## 2. Inbound: `0x0575`

### 2.1 Pinning the opcode, and the controls

`CField::OnPacket` = `FUN_141820080`. Opcodes `> 0x4B3` fall to a two-level table at
`141821a52`: `lea eax,[rdx-0x4d2] / cmp eax,0xd9 / ja default`, a **byte** index table at
`0x1418223C4` (218 entries) selecting one of **27** dword targets at `0x141822358`. [L]

Decoding both levels in full gives `opcode 0x0575 -> byteidx 9 -> 0x141821ac5 -> call
0x141C3D3E0`. `tools/callers.py` confirms `FUN_141C3D3E0` has exactly **one** caller in the
image, that call site. [L]

Three controls on that arithmetic:

1. **Structural.** `(0x18223C4 - 0x1822358) / 4 = 27`, and slot 26 is `0x141821e24`, which
   is the address both range checks already `ja` to - the decode reproduces the default from
   an independent direction. [L]
2. **Independent prior decode.** `research/storage.md` decoded *this same table* and pinned
   `0x0572 -> FUN_142159A90` (storage), corroborated there by ten storage string ids. My
   decode reproduces `0x0572 -> byteidx 6 -> 141821a9e -> call 142159a90` exactly. [L]
3. **Semantic.** Decrypting every string id reachable from `FUN_141C3D3E0` within two call
   levels: [L]

   | id | text |
   |---|---|
   | `0x01C5` | *"You can't establish a miniroom right here."* |
   | `0x01C6` | *"You can't open a minigame here."* |
   | `0x01C7` | *"Please invite later."* |
   | `0x01C8` | *"'%s' is doing something else right now."* |
   | `0x01C9` | *"'%s' has denied the invitation."* |
   | `0x01CA` | *"'%s' is currently not accepting any invitation."* |
   | `0x01CB` | *"'%s' is a character that cannot trade cash items."* |
   | `0x01E0` | *"You don't have enough mesos to enter."* |
   | `0x0205` | *"The password is incorrect."* |

   That is not a set a wrong table index produces.

### 2.2 The mode table

`FUN_141C3D3E0` reads `raw 4` = `u32 mode`, then `lea eax,[rdi-3] / cmp eax,0xa / ja
141c3d791`, jump table at `0x141C3D7E0`, **index = mode - 3**, 11 entries: [L]

| mode | target | shape |
|---|---|---|
| 3 | `141c3d464` | `u8 slot`, then **virtual**, then `u32`, `str`, `u16` |
| 4 | -> `FUN_141C3D980` | `u32 A`, `u32 B` (+ more when `A == 0`) - section 2.4 |
| 5 | -> `FUN_141C3E110` | **the invite** - section 2.3 |
| 6 | -> `FUN_141C3E360` | `raw 4`, then up to 8 `str` (all gated) |
| 7 | `141c3d791` (default) | virtual `[vt+0x178]`, mode passed in `edx` |
| 8 | `141c3d5bc` | virtual `[vt+0x198]`, no reads of its own |
| 9, 0xA | default | as mode 7 |
| 0xB | `141c3d612` | `u8 slot`, then virtual `[vt+0x1C8]` |
| 0xC | `141c3d6f1` | virtual `[vt+0x168]` |
| 0xD | `141c3d747` | virtual `[vt+0x1A0]` |

Anything outside `3..0xD` takes the default. Every mode first does an RTTI-style check on
the single global "current miniroom dialog" pointer (`0x143AA8520` region) against a
per-mode type descriptor, and returns silently if it does not match - so an inbound mode
sent while the wrong dialog (or none) is open is a **silent no-op**, not an error. [L]

### 2.3 Mode 5 - the invite. This is the one that makes the popup

`FUN_141C3E110`. `tools/reads.py 0x141c3e110 4` reports **exactly five reads, all direct,
none gated**, and the listing confirms the first conditional branch is at `141c3e176`,
*after* all five. So the body is complete and unconditional: [L]

```
141c3e13a  raw 4   -> type            (edi)
141c3e142  u32     -> X               (r15d)
141c3e155  str     -> inviter name
141c3e15e  u32     -> DISCARDED       (eax immediately overwritten)
141c3e166  u32     -> ticket          (r14d)
```

**Inbound `0x0575` mode 5, field by field:**

| # | width | field |
|---|---|---|
| 1 | `u32` | mode = **5** |
| 2 | `u32` | **type** - 1 = trade, 2 = cash trade [D] |
| 3 | `u32` | an id the client looks up locally; a hit auto-declines - see below |
| 4 | `str` | inviter's character name (u16 length prefix + that many bytes) [L] |
| 5 | `u32` | read and **discarded** - still must be sent |
| 6 | `u32` | **ticket** - echoed back in the accept/decline of section 1.3 |

**Total = 22 + len(name) bytes**, where `len` is the byte count after the 2-byte length
prefix. (`4 + 4 + 4 + (2 + len) + 4 + 4`.) The string primitive `1406E9050` reads
`movzx r8d, word ptr [rdx]` then that many bytes - **u16 length prefix**, confirmed in the
listing. [L]

**The popup gate, which is almost certainly the owner's missing popup.** Fields 2, 4 and 6 are
handed to `FUN_14180FA70(dlg, &name, ticket, type)` at `141c3e2b3`, and its first act is: [L]

```
14180fa9d  cmp r9d, 1        ; type
14180faa1  jne 14180faa9
14180faa3  lea eax,[r9+0x14] ;   type 1 -> balloon kind 0x15
14180faa9  cmp r9d, 2
14180faad  jne 14180fe32     ;   anything else -> RETURN, no popup, no error
14180fab3  mov eax, 0x16     ;   type 2 -> balloon kind 0x16
14180fab8  mov [rcx+0x300], eax
14180fabe  add rcx, 0x320    ;   copy the name
14180faca  mov [rbp+0x328], ebx  ; the ticket
```

Balloon kind `0x15` renders string `0x0439` *"Trade request from"*, kind `0x16` renders
`0x043A` *"Cash trade request from"* (`FUN_1418099F0` case `14180a94c`, `cmp edx,0x15`). [L]

Corroboration that {1, 2} really is the whole valid set: `FUN_140426CB0` is
`return n == 1 || n == 2;` in five instructions, and it is called on this same field on both
the inbound path (`141c3e1bc`) and the outbound menu path (`141826c40`). [L]

**So: `type = 0`, or 3, or anything but 1 or 2, produces no popup and no complaint.** A
server that sends the invite with a zeroed or wrongly-placed type field reproduces exactly
the symptom reported.

Field 3 is passed to `FUN_142D01050(manager, id)`, which is
`mov rcx,[rcx+0x3448]; xor r8d,r8d; jmp 1408CEF00` - a lookup of a `u32` id in a collection
at `manager+0x3448` on the global at `0x143AA84A0`. A **hit** (`test eax,eax / jne`) makes
the client auto-decline with reason 4 and never show the popup. The same helper has 19 call
sites across unrelated subsystems, so it is generic and I have **not** determined which list
this is. The inviter's character id is the natural candidate [I], but it is not measured.
Field 3 does not reach the popup - only 2, 4 and 6 do. [L]

### 2.4 Mode 4 - room open / notice

`FUN_141C3D980`, guarded at `141c3d9af` by `cmp qword [0x143AA84A0-ish], 0 / jne` - when
that global is non-zero the handler returns having read **nothing**. [L]

```
141c3d9c7  raw 4 -> A
141c3d9d9  raw 4 -> B
```

* **`A != 0`**: switch on `A - 6`, table at `0x141C3E094`, 29 entries covering
  `A = 6..0x22`; `7, 9, 0xA, 0xC, 0x10, 0x17, 0x18, 0x1D, 0x20, 0x21, 0x22` are the default.
  None of the reached cases reads any further field. **Body = 12 bytes**
  (`u32 mode=4, u32 A, u32 B`). Case `A = 6` shows *"That cannot be done in the current
  world."* (`0x12D6`), so `A` is a result/notice code. [L]
* **`A == 0`**: a **third** `raw 4` is read at `141c3df0d`, then the room window is created
  by `B`: `B == 1` -> `new(0x1678)` + `FUN_142146D90`; `B == 3` -> `new(0x1B40)` +
  `FUN_141E93230`; `B == 4` -> `new(0x1860)` + `FUN_141C145F0`. Any other `B` -> an error
  path, no window. Then `[room+0x304] = B`, `[room+0x308] = third`, and
  `FUN_141C3ED00(room, packet)` decodes the rest. [L]

`B == 1` selects the class whose own `0x017E` senders are `FUN_142147160` (mode `0x0C`) and
`FUN_14214B090` (mode `0x10`) - the trade dialog. So **roomType 1 = trade** in three
independent places: this table, `FUN_140426CB0`, and `FUN_14180FA70`. [D]

`FUN_141C3ED00` - the room-open payload, and the conditional the brief asked about: [L]

```
141c3ed25  u8   -> [room+0x2fc]                       unconditional
141c3ed38  u8   -> [room+0x2f8]                       unconditional
           ; 141c3ed70..141c3ee4f is a CLEARING loop over the 8 member
           ; slots at room+0x310 + i*0x38 - it reads nothing
repeat:
  141c3ee58/ef00  u8 slot
                  if (slot & 0x80) break              ; test al,al / js|jns
                  if ((u32)slot >= 8) break
  141c3ee87        virtual [vt+0x1C8](room, slot, packet)   ; per-room-type payload
  141c3ee97        u32  -> member[slot].id
  141c3eea9        str  -> member[slot].name
  141c3eeeb        u16  -> member[slot]+0x10
                  ++[room+0x300]
141c3ef3b  a final virtual call carrying the remaining packet
```

So the member list is **terminated by a negative `u8`** (0xFF by convention), not
length-prefixed. Each iteration costs `1 + <virtual> + 4 + (2+len) + 2` bytes plus the
1-byte terminator. **I have not decoded the `[vt+0x1C8]` payload**, so I cannot give a total
byte count for the room-open packet, and I am not going to guess one.

## 3. What I could not determine, and the blind spot in each case

1. **The bodies of inbound modes 3, 6, 7, 8, 0xB, 0xC, 0xD.** Each hands the remaining
   packet to a **virtual call** on whichever miniroom dialog is currently open. The dispatch
   is `[vt+0x168]`, `+0x178`, `+0x180`, `+0x198`, `+0x1A0`, `+0x1C8`. **The blind spot is
   that the body is not a property of the opcode+mode at all** - it depends on the object,
   and there are at least three (trade `142146D90`, and two mini-game classes
   `141E93230` / `141C145F0`). I resolved the **trade** class's vtable
   (`0x143431CC8`, from `142146db5 + 0x12eaf13`) and its slots are `+0x168 -> 141C3EF70`,
   `+0x178 -> 14214A9C0`, `+0x180 -> 14214AA80`, `+0x198 -> 141C3F300`,
   `+0x1A0 -> 141C3F7F0`, `+0x1C8 -> 141C423D0`. Their read *shapes* from
   `tools/reads.py ... 4` are below as **candidates, not bodies** - most reads are `gated?`
   and I did not read the branches, so building a packet from this table would be exactly
   the mistake that killed a client:

   | slot | function | reads (unverified branch structure) |
   |---|---|---|
   | `+0x168` | `141C3EF70` | `u8`, `raw` |
   | `+0x178` | `14214A9C0` | `raw`, `u8`, `u64`, then `u8` via `14214AE50` |
   | `+0x198` | `141C3F300` | `raw`, `u8`, `str`, `u8`, `str`, `str`, `u32`, `u32`, ... |
   | `+0x1A0` | `141C3F7F0` | `raw` |
   | `+0x1C8` | `141C423D0` | `u8`, `u32`, `raw` via `1402EE8D0` |

2. **Field 3 of the invite.** Measured as a `u32` looked up in a client-side collection at
   `<0x143AA84A0>+0x3448`, with a hit causing an auto-decline. Identity not established -
   the lookup helper is generic (19 call sites). Blind spot: I did not enumerate the writers
   of `+0x3448`; a `tools/fieldrefs.py 0x3448 --write` over the image would settle it, and
   did not finish inside my budget.

3. **Field 5 of the invite.** Read and discarded by the client. Four bytes must be present;
   its meaning is unrecoverable from this client because nothing consumes it.

4. **The `u8` in the outbound create** (`u32 0, u32 1, u8 0`). Always literal `0` on this
   path; nothing here says what a non-zero value means.

5. **Cash trade end-to-end.** Outbound is `0x02F8` (5 bytes), not `0x017E`, and inbound
   roomType `2` does not appear in the mode-4 room-creation switch (which handles only 1, 3,
   4). Where the cash-trade window comes from is not decoded.

6. **Mode names.** Every mode number above is [L]; the *names* I have attached (create,
   invite, accept, decline) come from the call sites and the string table, and are [D]. The
   mini-game modes `0x11`-`0x1C` are named only where a confirm-dialog string pins them.

## 4. Minimum the server has to do for a popup

Measured, in order, with byte counts. Nothing here is a guess about a body; where a body is
unknown it is called out above and is **not** listed.

1. Client A sends `0x017E` `u32 0, u32 1, u8 0` (9 B) - create a trade room.
2. Client A sends `0x017E` `u32 5, u32 targetCharacterId` (8 B) - invite.
3. Server sends B `0x0575`: `u32 5`, `u32 type`, `u32 id`, `str inviterName`, `u32 pad`,
   `u32 ticket` - **22 + len(name)** bytes. **`type` must be 1** (or 2 for cash trade) or no
   popup is built and no error is raised.
4. B answers `0x017E` `u32 3, u32 ticket, u8 0, u8 0` (10 B) to accept, or
   `u32 6, u32 ticket, u32 reason` (12 B) to decline.
5. The trade window itself needs `0x0575` mode 4 with `A = 0`, `B = 1`, a third `u32`, and
   the `FUN_141C3ED00` payload - whose per-member virtual portion is **not decoded**.

And the standing rule applies to every one of these: an unanswered packet freezes the whole
UI. `0x017E` is currently logged as `UNKNOWN ... not answered yet` in every archived run.
