# Omok rooms: the balloon, the visit, the leave reasons - and one correction

2026-10-04. Static, from `client-patched/MapleStory.exe`; the decompiles are
`research/msexe-omok-room.c`. Builds on `research/minigames-2026-09-09.md` (the moves) and
`research/miniroom-rooms-2026-09-09.md` (the room open). Implemented in `crates/net/src/minigame.rs`
and `crates/world/src/session/minigame.rs`. **Nothing here has been on a screen yet** - plan step 45.

The owner: *"I just tried opening up a minigame room for omok, it did not open, and it did not
advertise the minigame room in the map."* The create had arrived (`world-ch0.log`,
`00000000 03000000 0500 68656c6c6f 00 00` - Omok, "hello", public, set 0) and the server
only knew room type 1, so it logged it and sent nothing.

Tags: **[L]** read off the listing or decompile, **[D]** derived, **[I]** inferred.

## 1. The balloon is `0x0233`, `FUN_1427956b0`

Found by its **read shape**, not by a write scan. `research/user-pool-tables.md` row `0x0233`
(index `0x0d` of the `0x0226..0x0292` dispatcher) reads `raw u32 raw str u32 u8 u8 u8 u8
(str+raw)` - the same shape as `0x0224`'s optional miniroom block at `1429cee29`
(`research/user-enter-field.md` §2.3). The listing confirms it field for field. [L]

**The write scan missed it.** `python tools/fieldrefs.py 0x1118 --write` over the whole
image finds 9 writers, including `0x0224`'s `1429cee32`, and **not** this handler, which
writes through a `lea`'d pointer (`lea rcx,[r14+0x1118]` then `mov [rcx],eax`) - the
`mob+0x42c` blind spot `CLAUDE.md` describes, again. [L]

```text
u32    character id         the dispatcher's, then CUserPool::GetUser (reaches the local user too)
raw 4  room type   +0x1118  0 -> FUN_141596ea0 removes the balloon and NOTHING ELSE IS READ
u32    room id     +0x1120  sent back by a click (FUN_14276f790: mov eax,[rcx+0x1120])
raw 4  canEnter    +0x111c  'canEnter'/'cannotEnter' - the shop branch only
str    title       +0x1128
u32    game kind   +0x113c  Match Cards: icon_card%d
u8     private     +0x1130  icon_private / icon_public; a click asks for the password (FUN_14276f8d0)
u8     players in  +0x1138  number/cur/%d
u8     capacity    +0x1134  number/max/%d
u8     playing     +0x1140  status2 / status1
-- unless user+0x6ac != 0 (0x140f8abc0: cmp [rcx+0x5ac],0 on user+0x100):
chat-info block    FUN_1408d6760, then FUN_1415ed1c0(.., 0x1f): a "[Miniroom]" (0x1422) chat line
```

The names of the balloon fields come from `FUN_141594970`, which draws it: type 3 loads
`icon_omok`, type 4 `icon_card<kind>`, anything else `icon` with `canEnter`. [L] The chat-info
block is always sent: when the client skips it, the bytes are harmless trailing data; when it
reads it, they are owed.

## 2. Entering a room from its balloon is mode 3

`FUN_1428B7600` (the click on another user) builds `0x017E`: `u32 3, u32 user+0x1120,
u8 hasPassword, [str password], u8 0`. [L] The same mode a trade accept uses
(`u32 3, u32 ticket, u8 0, u8 0`), with the password where the accept has a zero. So the room
id the server puts in the balloon is the ticket it gets back; the server uses the owner's
character id for both.

## 3. The create, and what its last byte is

`FUN_142D4ABC0`: `u32 0, u32 roomType, str title, u8 hasPassword, [str password], u8 spec`.
For Omok `spec = itemId % 100` - **which Omok set** was used (`4080000` -> 0). [L] The server
echoes it into the room open's tail and the balloon's game-kind field.

## 4. Correction: Omok's `vt+0x180` reads 20 bytes

`research/minigames-2026-09-09.md` §5.2 says the tails of inbound mode 3 (`FUN_141E9A2B0` Omok,
`FUN_141C1B3C0` Match Cards) "read nothing extra (`reads.py` depth 6, both empty)". The
decompile of `FUN_141E9A2B0` calls `FUN_1402d1b50(record, packet)` - the `.pdata`-less
20-byte raw thunk that the **same file** names as `reads.py`'s blind spot in §0.2. [L] So
"a visitor sat down" (mode 3) is `u8 slot, avatar look, u32 id, str name, u16, raw 20`,
and a server built from the old row would have sent it 20 bytes short.

Same instrument, same blind spot, two sections apart. The row was written from the tool's
output; the section above it explained why that output is wrong for exactly this call.

## 5. The leave reasons (`0x0575` mode 0x0C) for an Omok room

`FUN_141C3EF70` reads `u8 slot, u32 reason`, clears that seat, then calls `vt+0x190` =
`FUN_141E9A5E0(room, slot, member, reason)`. [L]

* **slot is not the reader's own**: a "has left" chat line, the seat empties, the window stays.
* **slot is the reader's own**, by reason:

| reason | text | window |
|---|---|---|
| 1, 5 | `0x1EB` "You have left the room." | closes |
| 3 | game ended + "will automatically close in 10 sec." | closes itself after 10 s |
| 4 | `0x1F2` "The room is closed." | closes |
| 6 | `0x1E8` "You have been expelled." | closes |
| other | nothing | closes |

## 6. The buttons (`FUN_141E95720`), and what that means for the server

* **Ready** (`0x3f0`) sends `0x19` when the client's own flag is clear, else `0x1A`, and does
  **not** set the flag - the inbound `0x19`/`0x1A` does. The server echoes to both seats. [L]
* **Start** (`0x3e9`) sends `0x1C` only when `FUN_141c3f8a0` is positive. [L]
* **Leave** (`FUN_141E9C770`): during a game it toggles "leave after this game" (`0x17`/`0x18`,
  with the client's own flag); otherwise it confirms (`0x203`), sends `0x0C` and closes its
  own window (`vt+0x138(2)`). The server sends the leaver nothing. [L]
* Tie `0x11`, forfeit `0x13`, expel `0x1B`, undo `0x15` - each behind the client's own
  Yes/No. [L]

## 7. Mode 4 notice `0x14` is "The password is incorrect."

`FUN_141C3D980`'s notice switch: `0x14` -> `0x205`. The server uses it for a wrong password,
and `0x16` ("The room is already closed.") / `0x15` (full) as trade does. [L]

## What is still open

* **The `0x0A` the owner's client sends from the room open** (`u32 0x0A, u8 1`). Logged only.
* **`kind` in the `0x1D` result**: only `== 1` (draw) is branched on; a win is sent as 0.
* **The double-three rule**: the client shows the message and the server decides. The server's
  rule is the usual renju one (two threes that could each become an open four), applied to both
  players. Whether this client's vanilla server applied it to both is not known.

## 8. Match Cards (2026-10-04, later)

The owner asked for it beside Omok. Decompiles appended to `research/msexe-omok-room.c`.

* **The click** (`FUN_141C16CD0`): the FIRST card of a pair is turned by the clicker's own
  client and sent (`0x23, u8 1, u8 idx`); the SECOND is only sent, and the client waits. So the
  server relays a first card to the opponent only, and the second to both. Clicks are refused
  while the turn clock is above 10 000 ms - after a miss the clock is set to `0x2d50`, a 1.6 s
  pause. [L]
* **A miss turns itself back**: `FUN_141C262D0(room, idx, 1)` sets `room+0x17c4 = 1`,
  `room+0x17bc = now + 900`, and the tick (`FUN_141C1BF70`) turns both cards face down when it
  expires. No server packet. [L]
* **The faces** are formatted with `"%d"` into `UI/Minigame.img/MatchCards/card/<n>`, which
  has `0`..`14`: 15 faces, so 30 cards is every face twice. [L] The server draws `count / 2`
  faces at random and shuffles the pairs.
* **The time-out is sent by BOTH clients**: the tick sends `0x1E` when the clock reaches zero,
  whoever's turn it is (only the sound is gated on "my turn"). The server takes it from the
  player whose turn it is. Omok's `FUN_141E9AE60` was read as the same shape. [L]
* **The deal** (`FUN_141C1CA70`) and the visitor-entered tail (`FUN_141C1B3C0`, which reads the
  20-byte record like Omok's) are as section 4 above and `minigames-2026-09-09.md` §4.1 say.

## 9. The record, and a second correction: the result carries both records

`FUN_141E9BB10` (Omok) and `FUN_141C1C7E0` (Match Cards) END by reading seat 0's and then seat
1's 20-byte record through `FUN_1402d1b50`. [L] So the result is **45 bytes (a draw) or 46 (a
win)**, not 5 / 6 as `minigames-2026-09-09.md` §3.6 / §4.4 say - the same `.pdata` blind spot a
third time. A server that sent 5 / 6 would have ended every game on a short packet.

What the 20 bytes are: the side panel (`FUN_141C17290`) formats `+0x10` into the top box and
`+0x04`, `+0x0C`, `+0x08` into rows at y `0xa9`, `0xba`, `0xcb` (x `0x1c7` minus the text
width). [L] The panel's labels are baked into `UI/Minigame.img/Common/score` - rendered, it
reads **PTS** over **TOTAL W / L / D**. [L] So:

```text
+0x00  u32  not drawn; 1 here, as the v214 reference writes [I]
+0x04  u32  wins
+0x08  u32  ties
+0x0C  u32  losses
+0x10  u32  points
```

The owner, 2026-10-04: the record is kept **per game**. `store::minigame` keeps one row per
character and game (3 / 4). Points are this server's rule: 2000 to start, +10 a win, -10 a
loss, a tie leaves them.
