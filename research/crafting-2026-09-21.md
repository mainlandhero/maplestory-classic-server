# Crafting: the six professions, `0x02F6` out, `0x0398` back

Written 2026-09-21, from the client (Ghidra over `research/ghidra/msexe`) and its own WZ.
No client run. Tags: **[L]** read off the listing or the WZ bytes, **[D]** derived from the
decompilation, **[I]** inferred.

The owner, 2026-09-21, with two screenshots of the Crafting Journal: *"We need to implement
crafting in our server. After these quest completions, they should unlock the appropriate
crafting menu within the client"*, naming Chrishrama, Francois, JM From tha Streetz,
Mr. Thunder, Silas Irons and Vicious, and *"it says the user needs level 10 and the quest
completed to unlock that crafting tab."*

## 0. The answers, up front

| the client wants | packet | body |
|---|---|---|
| "start crafting this" | `0x02F6` | `u32 0, u32 profession, u32 recipeKey, u8 useAdditive, u32 count` (`count` = `0xFFFFFFFF` on **Craft All**) |
| "the animation finished, complete it" | `0x02F6` | `u32 3` - and nothing else |
| "I closed the window / cancel" | `0x02F6` | `u32 1` |
| the server's answer to the start | `0x0398` | `u32 4, u32 result` |
| the server's answer to the complete | `0x0398` | `u32 7, u32 result` |
| "forget the craft you were told about" | `0x0398` | `u32 5` (resets the window) or `u32 6` (clears the request latch only) |

`result` is `0` for success; the failure codes are in §4. Everything else the player sees -
the item, the mesos, the mastery bar - arrives on the packets this server already sends:
`0x0070` inventory operations, the meso stat change, and `0x0081` for the skill.

## 1. The professions are six ordinary skills, and the tab unlocks on the skill

`FUN_1401d24c0(profession)` is a six-case switch, **[L]**:

| profession | skill | quest that grants it | the station NPC |
|---|---|---|---|
| 0 Smithing | `92000000` | 80008 Silas Irons in Need of an Apprentice | 800010 Anvil |
| 1 Weaponcrafting | `92010000` | 80011 Mr. Thunder in Need of an Apprentice | 800011 Weaponcrafting Station |
| 2 Tailoring | `92020000` | 80014 Francois in Need of an Apprentice | 800012 Sewing Machine |
| 3 Woodcrafting | `92030000` | 80017 Vicious in Need of an Apprentice | 800013 Woodworking Station |
| 4 Leatherworking | `92040000` | 80020 JM From tha Streetz Looking for a Partner | 800014 Leatherworking Station |
| 5 Arcforge | `92050000` | 80023 Chrishrama in Need of an Apprentice | 800015 Arcane Station |

The quest column is `Act.1.skill.0.id` in each quest's own `questlines.txt` rows, alongside
`Act.1.exp 171`; every one of the six has `Check.0.lvmin 10`, which is the owner's *"the user
needs level 10"*. **[L]**

The tab is drawn unlocked when the skill's level is `>= 1`:
`FUN_1410e8140` calls `FUN_1428de230(user, FUN_1401d24c0(tab), 0)` and, on `< 1`, greys the
list and draws *"%s Level %d or higher is required to craft."* (`1410eb110`). **[D]** So
**nothing but the skill unlocks the tab** - no separate flag, no opcode.

`Skill/Skill_000.wz` ships `9200.img` .. `9205.img`, one skill each, `invisible 1`,
`common/maxLevel 10`. **[L]**

## 2. The recipe key is computed, and getting it wrong means nothing can be crafted

`Etc/CraftRecipe.img` is `<profession>/<craft level>/<index>`, 348 recipes. The loader
`FUN_1401d36b0` builds one object per recipe and writes its key first, `1401d3d0c`:

```text
*piVar11 = (level + profession * 10) * 1000 + index;
```

**[D]** from the decompilation, with the three `atoi`s of the node names above it. The
lookup `FUN_1401d49b0(mgr, out, profession, key)` then walks that profession's vector
comparing the key to the first int, so the key is the only thing on the wire that names a
recipe. `tools/dump_craftrecipe.py` writes `gm-handbook/craftrecipes.txt` with the same
formula and refuses to write if its controls do not reproduce.

The recipe object, at the pointer the vector stores (call it `P`; the allocation starts at
`P - 0x28` and carries two vtables) - all **[D]**, cross-read from `FUN_1401d1b00`:

| offset | field |
|---|---|
| `P+0x00` | key |
| `P+0x04` | profession |
| `P+0x08` | `CoolTimeSec` |
| `P+0x0c` | `Conditions.SkillCheck.SkillID` |
| `P+0x10` | `Conditions.SkillCheck.reqSkillLevel` |
| `P+0x18` | `ProcessTimeMS` |
| `P+0x1c` | `AdditiveItemID` |
| `P+0x20` | `AdditiveCount` |
| `P+0x24` | `Meso` |
| `P+0x28`..`P+0x30` | `Ingredients`, a vector of `(itemId, count)` u32 pairs |
| `P+0x40`, `P+0x44` | `Results.item`, `Results.count` |

`Results.exp` is the **mastery** exp a craft pays; the client does not read it (it never
computes the bar's numerator itself) - it is ours to apply.

## 3. The exchange, in order

The window is client-side. It sends, and the three modes are the first `u32` of the body:

* **mode 0**, `FUN_1410e9c00`: `u32 profession` (raw 4 bytes), `u32 recipeKey`,
  `u8 useAdditive`, `u32 count`. `count` is the quantity box (1..9999, `FUN_1410ea030`) and
  `0xFFFFFFFF` when the player pressed **Craft All**. **[L]** off `1410e9c00`'s listing.
* **mode 3**, `FUN_1410e9d20` / `FUN_1410e7eb0`: the body is just the `3`. It is sent by the
  window's per-frame update once `ProcessTimeMS` has elapsed since the start, through the
  same `FUN_142cc42d0(ctx, 200, 0)` request throttle everything else uses. **[L]**
* **mode 1**, `FUN_1410e9d90`: the body is just the `1`.

The client sets its own state: `state = 1` on send (`1410e92f6`), `state = 3` when the
server accepts, `state = 0` when it fails or finishes. **Every write of `window+0x348` is
inside the crafting window's own code** - scanned across the whole 0x13000-byte region - so
the server cannot drive the animation, only allow or refuse it. **[L]**

`0x0398`'s handler is `FUN_1410e7970`, reached from the user-pool table `D`
(`FUN_14289a3a0`, opcodes `0x02c5..0x039e`) at `op 0x0398 idx 0xd3 stub 0x14289d58b`.
**[L]**, `research/msexe-userpool-tables-raw.txt`. It reads a `u32` mode and then:

```text
mode 4:  u32 result   reply to mode 0.  0 -> state = 3, the bar starts filling
mode 5:  -             state = 0, the window resets
mode 6:  -             clears the request latch only
mode 7:  u32 result   reply to mode 3.  0 -> crafted++, the "n / m" line is redrawn, and
                      if crafted < count the window starts the NEXT one by itself:
                      state = 1 and another mode 0 goes out.  Plays "CraftingCompleted".
```

**So a multi-item craft is N start/complete pairs, not one.** The `count` in mode 0 is the
client's own loop counter; the server sees one craft per pair and should treat each pair as
one item. **[D]**

## 4. The result codes, and the exact sentence each one puts on the screen

`FUN_1410ec340(window, result, ...)` maps the code to a string id; decrypted with
`tools/dump_stringids.py`. **[L]**

| code | string id | what the player reads |
|---|---|---|
| 0 | - | nothing; success |
| 1 | 6026 | An unknown error has occurred. |
| 2 | 6053 | An error occurred. Please try again. |
| 3 | 6054 | You do not have enough materials to craft this item. |
| 4 | 6055 | You do not have enough inventory space to craft this item. |
| 5 | 6056 | Crafting Process is already underway. Please wait until it's finished before crafting again. |
| 6 | 6057 | Your skill level is not high enough to craft this item. |
| 7 | 6058 | You do not have enough mesos to craft this item. |
| 9 | 6059 | Crafting is only available near crafting tools. |
| 10 | 6078 | This function is currently unavailable. |

Codes `1,2,3,4,6,7,9` (the mask `0x2de` at `1410e7bb0`) also put the window back to
`state = 0`; code `5` leaves the state alone, which is why it must not be used for anything
but "you already have a craft running". **[L]**

## 5. Mastery: the level and the exp share one `u32`, and it is the skill record's

`FUN_1407b3df0` - the general "what level is this skill" - ends, for a skill that
`FUN_140823470` says is a mastery skill, with

```text
level = min(raw >> 24, maxLevel)
```

and `FUN_1407b5350`, the crafting window's exp getter, reads the same `raw` and takes
`raw & 0x00FFFFFF` as the exp, clamped to what the level needs. **[D]**, both off the same
`entry+0x14` of the skill hash.

> **The skill record's `level` field for `9200 0000`..`9205 0000` is
> `(level << 24) | masteryExp`.** Nothing else changes: it is the ordinary
> `net::skills::Skill` on the ordinary `0x0081` / character record.

The bar is `exp / need(level)` as a percentage, `FUN_1410ea110`, and `need` is
`FUN_1401d2320`, whose listing is unambiguous (`0x1401d2335 MOV EAX,0x32`,
`0x1401d2387 ADD EAX,0x64`, multiplier `[0x143273950] = 1.32` for levels up to 10):

```text
need(1)  = 50
need(n)  = trunc(need(n-1) * 1.32) + 100      n in 2..10
need(n)  = 0                                  n > 10
-> 50, 166, 319, 521, 787, 1138, 1602, 2214, 3022, 4089
```

**This disagrees with the table the owner sent** (meowdb's *Crafting EXP (Mastery) Table*:
50, 115, 199, 308, 450, 635, 875, 1187, 1593, 2120 - which is exactly
`trunc(prev * 1.3) + 50`). **Settled by the owner, 2026-09-21:** *"You can settle for the EXP
curve in the client, since that's the source of truth for the client display."* So the
client's curve stands and meowdb's table is not used. The two agree on everything else,
including the character-level gate below.

### The character-level cap

`FUN_1410ec9c0` draws *"To level up %s further, your character must be level %d or higher."*
with `(level + 1) * 5`. **[L]** So raising the profession to level `L` needs character level
`L * 5`, and level 1 is the quest's own `lvmin 10`. meowdb's column agrees
(`char_lv = 5 x craft_lv`), and adds that exp earned at the cap is **discarded**.

## 6. "Crafting is only available near crafting tools" is an NPC proximity test

`FUN_1401d2f70(user, profession)` looks the station up in the **NPC pool** by template -
`0xC350A + profession`, i.e. **800010..800015** - and returns true when
`|npc.x - user.x| < 90` and `npc.y` is within `[user.y - 50, user.y + 50)`. **[D]**
The 19 placements are already in the client's own map data
(`gm-handbook/npcs.txt`: Anvil, Weaponcrafting Station, Sewing Machine, Woodworking Station,
Leatherworking Station, Arcane Station), so this server spawns them with every other NPC and
has nothing to place.

The client refuses to send at all when the test fails, so a server-side proximity check is a
second opinion rather than the gate. This server keeps one anyway (code 9), because
**nothing authenticates** - the game socket carries no credentials and a crafted `0x02F6`
body is free.

## 7. What is NOT known

* ~~What opens the window.~~ **Answered on screen, 2026-09-21**: *"The crafting UI is opened
  by a keybind via the client."* No packet does it - `0x0398`'s handler never creates the
  window, and the two refresh entries (`FUN_1410ec8c0`, `FUN_1410ec930`) are called from the
  `0x0081` skill handler and from an inventory notification, i.e. they re-draw one that
  already exists. So the Journal opens anywhere, and a greyed tab with its *"is looking for
  an apprentice"* line is the only thing gating a profession.
* **Whether a station click sends anything.** If it sends the ordinary NPC-select packet,
  this server answers it the way it answers any NPC with nothing to say.
* **A quest finished before this server read `Act.1.skill` grants nothing by itself**, and a
  completed quest is never turned in again - which is what the owner saw on 2026-09-21, a
  level-12 character whose Woodcrafting tab still read *"Vicious in Henesys is looking for an
  apprentice"*. `Session::reconcile_crafting_quests` backfills at the claim, at level 1 with
  an empty bar; the mastery those turn-ins would have paid is **not** replayed, because a
  login that adds mastery is a farm.
* **`Results.exp` at the character-level cap.** meowdb says overflow is discarded; that is
  the behaviour implemented, and it is [I] for this client.
