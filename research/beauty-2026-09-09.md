# Hair and face coupons: the items, the legal values, and why `0x0138` cannot deliver them

**2026-09-09. No Ghidra** (the project lock was withheld). Everything below came from
`client-patched/MapleStory.exe` through `tools/listing.py`, `tools/reads.py`,
`tools/dis_at.py`, `tools/callers.py`, `tools/dump_va.py` and `tools/xref.py`, from the
client's own WZ through `target/release/wz-dump`, and from reading `crates/` (nothing in
`crates/` was modified). One new tool, `tools/dump_beauty.py`, writes
`gm-handbook/beauty.txt`.

Labels are the project's: **[L]** read off this client's listing or its own data ·
**[D]** derived from two or more [L] facts · **[I]** inferred, not established.

## 0. Answer up front

| question | answer |
|---|---|
| which items are the coupons | **ten, `05150000`..`05153000`**, all in `Item/Cash/Cash_000.wz` `0515.img` — the **cash** region. `Item/Consume` has none. **[L]** |
| what their data says they do | **nothing.** Every one is `info = { icon, iconRaw, cash: 1 }`; `05152100` adds `choice: 1`. No hair node, no face node, no script node. The behaviour is entirely the server's to define. **[L]** |
| where the candidate style lists live | `Etc/Etc_000.wz` **`BeautyPreview.img`** — coupon id → candidate ids, split `MaleHair` / `FemaleHair` / `MaleFace` / `FemaleFace`. 12 lists, 186 ids. **[L]** |
| legal hair ids | **1272**, `30000`..`31807`. **159 bases × 8 colours**, colour = `id % 10` ∈ 0..7, exactly, no exceptions. 81 male bases (`30xxx`), 78 female (`31xxx`). **[L]** |
| legal face ids | **468**, `20000`..`21825`. **52 styles × 9 eye colours**, eye colour = `(id / 100) % 10` ∈ 0..8, style = `id % 100`, exactly, no exceptions. 26 male styles (`20xxx`), 26 female (`21xxx`). **[L]** |
| does gender restrict the id | **No, not in the client.** Hair art resolves through the format string `Character/Hair/%08d.img` and face through `Character/Face/%08d.img` — **one `%08d` of the id, gender is not in the path**. A `30xxx` hair on a female character draws *male hair*, not nothing. Only an id with no `.img` is invisible. **[L]** |
| `0x0138 UserAvatarModified` body | `u32 characterId` + the 195-byte compact look = **199 bytes** with no equips, **+5 per equipped item**. **[L]** for the read count and widths, **[D]** for the total. |
| does `0x0138` redraw anybody | **No. It applies nothing at all.** Not the equipment, not the hair, not the face. The look pointer reaches exactly one instruction in the apply and that instruction is behind a guard that always fails. **[L]**, re-derived here — §4.2. |
| is a coupon double-clicked (`0x010E`) | **Undetermined, and probably not.** `0x010E` exists and reaches the server; nothing establishes that the client *builds* one for a `05xxxxx` cash item, and the UI evidence points at a button instead. See §5.4 and §7. |
| the best candidate for the coupon packet | `0x03E1` sub-op **`0x32`** (`raw[8]` cash-item SN) and sub-op **`0x3d`** (`raw[8]` SN + `u32`), both newly decoded here. Shapes **[L]**; that they are the beauty ops is **[I]** and unproven — §5.3. |
| is it NPC-driven | **Not through any dialogue this client can draw.** All **71** entries of the `0x055B` message-type table are enumerated and **none of them carries a style list** — no count-prefixed `u32` array anywhere, including the five previously-undecoded types `0x42..0x46`, which this file decodes. **[L]** |
| so where does the picker live | **a Beauty Room UI reached from the Equip window's Cash tab.** The client carries `UI/UIWindow4.img/Equip/Cash/**BtBeautyRoom**` (a button), a nine-node `UI/CashShop.img/**CSBeauty**/…` window with `avatarBg`, `hairColor/base|Enable|Disable`, `eyeColor/base|Enable|Disable`, `tip/hair`, `tip/face`, plus `UI/CashShopUI.img/BeautyPreview` and `UI/UtilDlgEx.img/UtilDlgEx_Beauty`. **[L]** These are resource paths, not a decoded packet — see §5.2. |

**The headline for the server, and it is a negative:** there is no cheap "you now have this
hair" packet. The character's appearance is rebuilt from the look it is *given on entry* —
`SetField` for the local player, `0x0224 UserEnterField` for everyone else — and `0x0138`,
the packet whose whole purpose is to change it in place, is dead code.

## 2. The coupons

### 2.1 The ten items — `Item/Cash/Cash_000.wz` → `0515.img` **[L]**

```text
05150000  Mystery Hair Coupon                    info: cash
05150100  Signature Hair Coupon                  info: cash
05151000  Mystery Hair Color Coupon              info: cash
05151100  Signature Color Coupon                 info: cash
05151200  Custom Mix Dye Coupon                  info: cash
05152000  Mystery Face Coupon                    info: cash
05152100  Signature Eye Color Coupon             info: cash, choice
05152200  Signature Face Coupon                  info: cash
05152300  Custom Colorblend Eye Color Coupon     info: cash
05153000  Signature Skin Color Coupon            info: cash
```

Names from `String/String_000.wz` → `Cash.img` (already in `gm-handbook/items.txt`).

**The region is load-bearing.** These are in `Item/**Cash**/Cash_000.wz`, not
`Item/Consume/Consume_000.wz`. A search of the consumables region for a coupon returns
nothing, and that empty result is a property of the search.

**`info` carries no behaviour.** `cash: 1` marks it a cash item; `choice: 1` on `05152100`
is the only other scalar in the whole image. There is no `hair`, no `face`, no `skin`, no
`scripts`, no `time`, no `mcType`. Compare `tools/dump_chairs.py`'s subject, where
`recoveryHP`/`recoveryMP`/`reqLevel` are all present — the client's data *does* describe
item behaviour when there is behaviour to describe. Here it does not, so nothing about what
a coupon does can be read out of the item.

### 2.2 Eight of the ten are sold — `Etc/Etc_000.wz` → `Commodity.img` **[L]**

```text
150000000  05150000  100 NX  gender 2  onSale 1
150000001  05150100  100 NX  gender 2  onSale 1
150100000  05152000  100 NX  gender 2  onSale 1
150100001  05152200  100 NX  gender 2  onSale 1
150200000  05153000  100 NX  gender 2  onSale 1
150200001  05151000  100 NX  gender 2  onSale 1
150200002  05151100  100 NX  gender 2  onSale 1
```

`05151200` (Custom Mix Dye) and `05152300` (Custom Colorblend Eye Color) have **no sale
row**. That is a fact about this client's shop, not a missing read — the other eight came
out of the same walk. `gender 2` = either gender, on all eight.

### 2.3 What each coupon offers — `Etc/Etc_000.wz` → `BeautyPreview.img` **[L]**

| MaleHair | `5150100` | 16 | same 16 as `5150000` |

| FemaleHair | `5150000` | 19 | `31030 31040 31050 31070 31080 31100 31110 31150 31160 31170 31260 31270 31280 31290 31300 31310 31350 31360 31380` |
| FemaleHair | `5150001` | 19 | `31010 31020 31060 31090 31120 31130 31140 31180 31190 31200 31210 31220 31230 31240 31250 31320 31330 31340 31400` |
| FemaleHair | `5150100` / `5150101` | 19 / 19 | same two lists again |

Three things fall out, and the second is the kind that gets missed:

* **The candidates are base ids** — every hair entry ends in `0`, every face entry is at eye
  colour `0`. Colour is chosen separately; §3 gives the arithmetic.
* **The preview keys are a superset of the items.** `5150001` and `5150101` have full
  candidate lists but **no item in `0515.img` and no row in `Commodity.img`**. Enumerating
  `BeautyPreview.img` finds them; starting from the ten item ids and looking each one up
  does not. This is `CLAUDE.md`'s *enumerate before you filter*, and it changes the shape of
  the server's table from "ten coupons" to "a coupon→list map with twelve keys".
* **`Skin` is empty**, so `05153000` (Signature Skin Color Coupon) has **no client-side
  candidate list at all**. The skin values that *are* named by the client are the four in
  `Etc/MakeCharInfo.img`: `12000` Light, `12001` Tan, `12002` Dark, `12003` Pale. **[L]**

`tools/dump_beauty.py` writes all of §2 and §3 to `gm-handbook/beauty.txt`.

## 3. The legal hair and face values

### 3.1 Enumerated from the art, not from a list **[L]**

`Character/Hair/Hair_000.wz` holds **1272** `.img` nodes, `Character/Face/Face_000.wz` holds
**468**. One node per id. Those two counts are the definition of "will draw".

Both decompose with **zero exceptions** — asserted in the dumper, which refuses to write if
either breaks:

```text
hair   id = base + colour        base = id - (id % 10)        colour in 0..7
       159 bases × 8 = 1272      30xxx: 81 bases (male)       31xxx: 78 bases (female)

face   id = style + 100*eye      style = id % 100             eye in 0..8
       52 styles × 9 = 468       20xxx: 26 styles (male)      21xxx: 26 styles (female)
```

So a **hair colour** change is `base + newColour`, and an **eye colour** change is
`(id / 1000) * 1000 + (id % 100) + 100 * newColour`. No second table is needed for the
colour coupons, and that is a measured property of this client's data rather than a
convention borrowed from elsewhere.

### 3.2 No placeholders **[L]**

The smallest hair image is **4713** bytes and the smallest face image **6919**. Neither
archive contains a 13-byte stub of the kind `Item/Cash/Cash_000.wz` is full of (`0506.img`,
`0510.img`, `0521.img`, … are all 13 bytes). So in *this* client "present in the tree" and
"has art" are the same statement. `tools/dump_beauty.py` checks it anyway
(`MIN_IMAGE_BYTES`), because that equivalence is a property of the client, not of WZ.

### 3.3 Gender is not enforced by the client **[L] + [D]**

The client builds the art path from a format string:

```text
Character/%08d.img
Character/Face/%08d.img
Character/Hair/%08d.img
Character/Cap/%08d.img
...
```

(UTF-16, one contiguous run in `.rdata`.) **One `%08d` of the id and nothing else.** Gender
is not in the path, so the composer cannot be consulting it at lookup time. **[L]**

The packet side agrees: `FUN_1402ee8d0` validates the *equipment* pairs — `FUN_140253980(itemId,
slot, 2, 1)`, silently dropping failures (`research/naked-character.md` §4) — but reads
`hair` as a bare `u32` into equipment slot 0 and `face` as a bare `u32`, with no call
between them. **[L]**

**[D]** therefore: a wrong-gender hair id renders the wrong-gender hair. It is a
correctness bug on screen, not an invisible character. The server should still constrain by
range, but for the right reason.

> **The bound on that negative.** It says the *art lookup* and the *packet decode* do not
> consult gender. It does not say no code anywhere gates on it — a UI that offers styles
> would obviously filter by gender, and `BeautyPreview.img` is split by gender precisely so
> it can. **[I]**

### 3.4 One thing already in the repo that this contradicts

`crates/login/src/session.rs:1947-1950` asserts a stored character with
`hair == 30030`, `face == 21002`, `gender == 1`. **`30030` is a male hair base
(`Shaved Hair`) on a female character with a female face.** By §3.3 that draws male hair on
a female body rather than nothing, which is why nobody has noticed. It is a test fixture,
not shipped data — recorded here because it is the first thing a hair validator would
reject, and I did not touch `crates/`.

## 4. `0x0138 UserAvatarModified`, decoded

### 4.1 The body, field by field, with the read count

Inbound dispatch, from the game-stage case table `research/msexe-gamestage-cases.txt:176`:
**`0x0138` → `FUN_142d012e0`**. **[L]**

`python tools/reads.py 0x142d012e0 6` — **depth 6, not 3**:

```text
FUN_142d012e0  0x142d012e0..0x142d01519 (569 bytes)  depth 6
  0x142d0131a  READ u32 (direct)
  0x142d01490  call 0x1402ee8d0 -> READS via helper: u8 u32 raw  gated?
```

Two read sites in the handler: a `u32` character id, then the compact-look reader. Nothing
else in the 569 bytes touches the packet — confirmed against the full listing, which shows
`0x142d01495 lea rdx,[rsp+0x30] / mov rcx,r15 / call 0x142797be0` immediately after and then
only scope-guard teardown. **[L]**

`python tools/reads.py 0x1402ee8d0 6` gives **24 read sites and no helper reads even at
depth 6**, at exactly the addresses `research/avatar-look-loops.md` §1 lists from depth 3.
Two loops, both terminated by a **one-byte** `0xFF`. **[L]**

```text
off  width  field                                    read at
  0  u32    characterId                              142d0131a   <- the handler's own read
  --- FUN_1402ee8d0, the compact look ---------------------------------------------
  4  u8     gender                                   1402ee8f3
  5  u8     skin                                     1402ee8fe
  6  u32    (discarded)                              1402ee90c
 10  u32    face                                     1402ee917
 14  u32    job                                      1402ee922
 18  u8     (discarded)                              1402ee994
 19  u32    hair          -> equipment slot 0        1402ee99c
 23  loop 1: u8 slot (1402ee9a7 / 1402ee9e8), u32 itemId (1402ee9b6), 5 bytes/entry
        u8 0xFF terminates                                            1 byte
        loop 2: same shape (1402ee9f7 / 1402eea3b, 1402eea06)
        u8 0xFF terminates                                            1 byte
  --- tail, 174 bytes, all fixed ----------------------------------------------------
        u32 ×4                    1402eea4a 55 60 6b
        u32 (taken mod 360)       1402eea79
        u8                        1402eeaac
        u32                       1402eeabf
        raw 4                     1402eeada
        raw 128                   1402eeaef
        u32                       1402eeaf7
        raw 13   (the name)       1402eeb12
```

**Byte count.** `4 + 195 = 199` with both maps empty, **+5 per equipped item**. **[D]** —
the 195 is 19 head + 2 terminators + 174 tail, and it is corroborated three ways: the
arithmetic over `net::opcode::avatar_look`, `research/avatar-look-loops.md` §3's field-by-field
walk of a 674-byte `0x0224` that the client accepted (`220 = 195 + 5×5`), and
`net::userpool::USER_ENTER_FIELD_LOOK_AT`. `crates/net/src/opcode.rs::user_avatar_modified`
already builds exactly this. **No byte of the builder needs to change.**

### 4.2 And it applies nothing. Re-derived, and it is stronger than the note in `crates/`

`crates/net/src/opcode.rs:1066` says the *equipment apply* is dead. It is broader than that.

`FUN_142797be0(user, look)` receives the look in `rdx`. `python tools/listing.py 0x142797be0`
is 866 bytes and `grep r15` over it returns **four** lines:

```text
000142797bf0  push     r15
000142797bf6  mov      r15, rdx          ; the look pointer, saved
000142797def  mov      rdx, r15          ; the ONLY use
000142797f39  pop      r15
```

Everything else in those 866 bytes is a walk of the intrusive list at `[user+0x1200]` with
refcount and lock bookkeeping. And the one use sits here:

```text
000142797dd2  mov      rbx, qword ptr [rsi + 8]
000142797ddb  test     rbx, rbx
000142797dde  je       0x142797e07          ; skip
000142797de0  mov      ecx, dword ptr [rbx + 0x30c]
000142797de6  call     0x1407f5ce0
000142797deb  test     eax, eax
000142797ded  je       0x142797e07          ; ALWAYS TAKEN
000142797def  mov      rdx, r15             ; <- the look, reached only past that jump
000142797df2  call     0x1420dd920
000142797dfa  mov      edx, 1
000142797dff  call     0x1420dd220
```

`python tools/dis_at.py 0x1407f5ce0 16`:

```text
0001407f5ce0  xor      eax, eax
0001407f5ce2  ret
0001407f5ce3  int3    ...
```

**[L]** Three bytes, unconditionally zero, followed by padding. `TEST EAX,EAX / JZ` after it
is therefore always taken, so `142797def` is unreachable, so **the look pointer is never
dereferenced on any path**. The packet is parsed in full — all 199+ bytes are consumed, so
it does not desynchronise — and then discarded.

> `/OPT:ICF` means that 3-byte stub is probably shared across the image, so the original
> function's name is unrecoverable. That does not weaken the branch. **[L]**

The consequence, and it is the one that decides the feature: **`0x0138` cannot deliver a
hair change to anybody — not the player who bought the coupon, not the people watching.**
No trigger, no ordering and no field value changes that.

### 4.3 The full set of inbound paths that read a compact look — enumerated

`python tools/callers.py 0x1402ee8d0` gives **17 call sites in 16 functions, 0 tail jumps, 0
data pointers**. Intersected against the two case tables (`research/msexe-gamestage-cases.txt`,
`research/msexe-loginstage-cases.c`), the entries that are reachable from a packet are:

| path | opcode | what it does with the look |
|---|---|---|
| `FUN_142d012e0` | `0x0138` | **nothing** — §4.2 **[L]** |
| `FUN_142d95ab0` | `0x0107` | formats 32 `"[BP:%02d] %d"` lines into the client's own log; applies nothing (`research/naked-character.md` §5.2) **[L]** |
| `FUN_142da4820` | `0x0114` | builds a separate 0x4b8-byte object; never reaches the avatar apply **[D]** |
| `FUN_1429ce270` | `0x0224 UserEnterField` | the **remote** user's look, at body offset `187 + 23 + name.len()` **[L]** |
| `FUN_1403094b0` | login-stage character list | dresses the character-select screen **[L]** |

The other eleven callers are not inbound handlers. **This is the whole set**, which is what
makes the negative in §0 worth stating: nothing in it re-dresses a character who is already
standing on a field.

## 5. The flow

### 5.1 It is not an NPC dialogue. All 71 message types enumerated **[L]**

`0x055B`'s message type indexes a **71-entry** jump table at `0x141f6f9f4`
(`python tools/dump_va.py 0x141f6f9f4 300` — 71 dwords then `cc cc cc cc` padding).
`research/script-reply.md` §6.1 decoded all but five, leaving `0x42..0x46` as
"these five also receive `handle`", bodies unread. Those five are the only place a style
list could have hidden, so they are decoded here.

Table entries 66..70 are five 16-byte arms at `0x141f6f974`, `..984`, `..994`, `..9a4`,
`..9b4`, each `mov r8,rbx / mov edx,r15d / mov rcx,rdi / call <handler>`:

| type | handler | `tools/reads.py <h> 4` |
|---|---|---|
| `0x42` | `FUN_141f765d0` | `u8, u32` |
| `0x43` | `FUN_141f76920` | `u8, u8, u32` |
| `0x44` | `FUN_141f76c80` | `u8, u8, u32, u32` |
| `0x45` | `FUN_141f76ff0` | `u8, u8, u32` |
| `0x46` | `FUN_141f77350` | `u8, u8, u32, u32` |

**All fixed-width scalars. No count, no loop, no string.** Verified on `0x44` against the
listing: the four reads are straight-line at `141f76cc8`, `..cd6`, `..ce4`, `..cf5` with no
backward branch between them, and the last `u32` is handed straight to a pool lookup
(`FUN_141e768f0`) as an id.

**[L]** So no `0x055B` message type carries a list of avatar candidates, and the salon-NPC
shape — server sends N styles, client renders each on the character, player picks one — is
not something this client can draw. A beauty NPC can *talk*, and can offer a `type 6` menu
of text lines, but cannot show the styles.

### 5.2 There IS a beauty UI, and it hangs off the Equip window's Cash tab **[L]**

Searching the image for `BeautyPreview`: **0 ASCII hits, 1 UTF-16 hit**. The ASCII-only
answer would have been "absent", which is why the control matters — everything in this
section would have been missed by an ASCII grep.

Enumerating every occurrence of `Beauty` in both encodings, rather than looking one string
up, gives the whole feature at once. **[L]**, all of it:

```text
UTF-16
  UI/UIWindow4.img/Equip/Cash/BtBeautyRoom      <- a BUTTON, on the Equip window's Cash tab
  UI/CashShop.img/CSBeauty/avatarBg             <- the salon window itself
  UI/CashShop.img/CSBeauty/detailBg
  UI/CashShop.img/CSBeauty/hairColor/base
  UI/CashShop.img/CSBeauty/hairColor/Enable
  UI/CashShop.img/CSBeauty/hairColor/Disable
  UI/CashShop.img/CSBeauty/eyeColor/base
  UI/CashShop.img/CSBeauty/eyeColor/Enable
  UI/CashShop.img/CSBeauty/eyeColor/Disable
  UI/CashShop.img/CSBeauty/tip/hair
  UI/CashShop.img/CSBeauty/tip/face
  UI/CashShopUI.img/BeautyPreview
  UI/CashShopUI.img/BeautyPreview/colorPalette/hair    (as two spliced literals)
  UI/CashShopUI.img/BeautyPreview/colorPalette/face
  UI/UtilDlgEx.img/UtilDlgEx_Beauty[/backgrnd]

  ETC_CharBeautyAPIInfo

  Replace Beauty Salon Appearance

```

Read structurally, that is a complete salon: an avatar preview, an `Enable`/`Disable` state
per colour swatch, a separate palette for **hair colour** and **eye colour**, and tips keyed
`hair` / `face`. It maps one-to-one onto §2.3 (`MaleHair`/`FemaleHair`/`MaleFace`/`FemaleFace`
lists of *base* ids) and §3.1 (colour chosen separately as an offset). **[D]**

**What I could not carry further, and why.**

* `tools/xref.py --va` finds **0 code references** to `BtBeautyRoom`, `[BeautyData]`,
  `CSBeauty/avatarBg`, `UtilDlgEx_Beauty` and `UI/CashShopUI.img/BeautyPreview`, and exactly
  **1** to `/colorPalette/hair` — `FUN_1400536b0`, a 64-byte static initialiser with 0 call
  sites and 1 data pointer (`0x143267590`, slot 2195 of a 7392-slot run). These are C++
  static-constructed string globals; the code reads the *global*, not the literal, which is
  `xref.py`'s own documented blind spot. Walking one of them (`tools/dataref.py 0x143ac9f40`)
  reaches `FUN_1410ad580`, `FUN_1410b0140`, `FUN_1410b0220`, `FUN_1410b1360` — and
  `tools/encodes.py` at depth 3 shows **not one packet primitive in any of the four**. They

* `research/msexe-send-opcodes.txt` (1881 of 1894 call sites resolved) lists **107** builders

* **`tools/ripstrings.py` failed its own documented positive control** — its docstring says

  it printed `0 lea targets decoded as text`. Whatever it said about these functions is

### 5.3 Four `0x03E1` sub-op builders, two of them new — shapes measured, meaning not

`research/cash-shop-stage.md` §5.2 read six of the **22** `0x03E1` builder sites and
`research/cash-shop-actions.md` named five sub-ops. Four more sit in the same UI region as the
cash-item windows. Sub-op bytes read by hand off `tools/dis_at.py`, bodies from
`tools/encodes.py` (control passed: `0x141cb6880 1` → CTOR `141cb7eb1`, and note the tool
correctly labels `0x1406ED610` `~COutPacket (NOT the send)`):

| builder | sub-op | body after the sub-op byte | status |

| `FUN_14103d780` | `0x1b` | a string built from string ids `0x21b`/`0x21c`, then `raw` | new |
| `FUN_14103dd50` | `0x1c` | `raw[8]` | **already decoded** — `cash-shop-actions.md`: *delete a cash item, `raw[8] SN`* |

The `0x1c` row is the point of the table: it is an **independent re-derivation of a sub-op
this repo had already decoded another way**, so the reading method behind the other three

`0x32` is "a cash item, by SN" and `0x3d` is "a cash item, by SN, plus one `u32`" — which are

this id) would take. **That is [I] and nothing more.** These four builders sit in the same

reached from the beauty UI, and the ripstrings pass that would have shown which strings they
touch is the one whose control failed.

### 5.4 `0x010E` is *a* path, and is not established to be *the* path

`0x010E` is fully wired server-side (`crates/net/src/useitem.rs:40`,
`crates/world/src/session/consume.rs`): body `u32 tick, i16 slot, u32 itemId, u32 tail`,
**14 bytes**, and every refusal path already answers with an empty `StatChanged` so the
client's request latch clears. A `05xxxxx` id double-clicked today lands in the
`consume.rs:68` refusal arm — the server answers, and says the item restores nothing.

What is **not** established is that the client builds a `0x010E` for a cash item at all.
Nothing in this pass looked at the double-click dispatcher. Given §5.2 — a `BtBeautyRoom`
**button** on the Equip window's Cash tab — **[I]** the gesture is more likely "click the
Beauty Room button, pick a style, confirm" than "double-click the coupon".

### 5.5 Nothing in the repo can write hair or face today

`hair`, `face` and `skin` are written in exactly one statement in `crates/store` — the
`INSERT` in `create_character` (`crates/store/src/character.rs:92-160`). `save_character_progress`
deliberately excludes them (`character.rs:313`: *"neither are name, face or hair, which are
not earned"*). There is no `UPDATE` that touches them. A change needs a new single-column
`Store` method on the `set_character_map` pattern (`character.rs:295-299`).

The data-driven script layer cannot do it either: `data/quest-scripts.txt`'s only
field-writing action is `Act.<state>.hp` → `Session::apply_quest_hp`
(`crates/world/src/session/npc.rs:570-590`), which writes HP and nothing else.
`data/npc-dialogue.txt` is a **text overlay** with no actions at all.

## 6. What the server must send

Not a new packet — a re-entry. In order:

1. **Persist** the new `hair` / `face` / `skin`. New `Store` method; nothing existing writes
   them.
2. **Redraw the player.** The only mechanism this client offers is the look it is handed on
   field entry, so the change lands on screen at the next `0x01A0 SetField`
   (`crates/net/src/opcode.rs:1768`) whose character record carries the new value. A
   same-map `SetField` is the cheap form and **is not tested** — see §7.
3. **Redraw everyone else's copy of the player.** `0x0225 UserLeaveField` (`u32 characterId`,
   4 bytes) followed by `0x0224 UserEnterField` rebuilt from the new look. `avatar_look()`
   needs no change; the look sits at `USER_ENTER_FIELD_LOOK_AT + name.len()` inside the body.
4. **Do not send `0x0138`.** It parses and discards — §4.2. Sending it costs bytes and
   changes nothing, and it will read on screen exactly like a broken feature.
5. **Answer the coupon use whatever happens.** Whichever gesture turns out to carry it, the
   `CLAUDE.md` rule applies; `consume.rs`'s `use_refused` is the shape to copy.
