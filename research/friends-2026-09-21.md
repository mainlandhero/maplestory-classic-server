So the client did send it, with the target's name and the group, and **this server has no
friend code at all** - `0x0193` is not in any handler, the request went unanswered, and
nothing came back to either screen. Not a regression: it has never existed.

`0x0193` appears **once** in the whole run, which is the control: the click produces exactly
one packet and nothing else (the grep is for that opcode specifically, not for "anything new
in the log" - `CLAUDE.md`'s cash-shop lesson).

**Nothing authenticates.** The game socket carries no credentials, so a `0x0193` body naming
any character is free; a friend list would have to check the name against the store like every
other request here.

## 2. What the client accepts back on `0x0193`, and it is NOT a list

`research/msexe-gamestage-cases.txt`: `0x0193 FUN_142d1ba10`. **[L]** Its body:

```text
u32  kind        raw 4 at 142d1ba2a, kept locally
u32  a           -> mgr+0x00     FUN_1401d7710, the whole decoder
u32  b           -> mgr+0x04
u32  c           -> mgr+0x08
str  name        -> mgr+0x10

```

Five reads, and `tools/reads.py 0x1401d7710 4` agrees with the listing on all five. **One
entry, not a vector** - there is no count anywhere in it. `kind == 7` builds the string
`"Not Find"`; any other kind, with `mgr+0x4130` non-zero, sets the byte at `mgr+0x4108` and
returns, which is what a "there is a request waiting" flag looks like. **[D]**

## 3. ANSWERED: the list rides the game socket, and the reply is `0x00A7`

The question was whether the friend window is fed by the game socket or by the client's
Nexon social layer. **Game socket.** The walk, all **[L]** unless marked:

1. The friend window (`FUN_1411c4c30`, the add button; `FUN_1411c0500`, the group sender)
   reads its rows through `FUN_142deda90(ctx, out)`, which walks the container whose pointer
   lives at **`ctx+0x23C8`**.
2. `tools/fieldrefs.py 0x23c8 --lo 0x142c00000 --hi 0x142f00000` names every function that
   touches it - 23 of them, the context's friend API, `0x142dec8f0`..`0x142def9c0` - and
   **exactly one of them is a packet handler**: `FUN_142defd40`.
3. `research/msexe-gamestage-cases.txt` line 47: **`0x00a7  FUN_142defd40`**.

So the pair is **`0x0193` out, `0x00A7` in**, and the `CNM*Friend*` functions are the
account-level *"Account Friends"* service - a different feature, not this window. The only
reference to any of those names is a data table at `0x141e24500`; nothing in the friend UI
reaches them. **[D]**

### `0x00A7`'s shape

`u8` sub-op first (`0x142defd7d`), then a case per kind - **34 cases, `0x15`..`0x36`**, which
sits exactly above the client's `1`..`0x14`, so requests and results share one enum. **[L]**
The three decoded so far:

| sub-op | body | what it does to the client |
|---|---|---|
| `0x19` | `u32 count, count x { u32 characterId, str name }` | **the whole list**: clears the container and refills it, then refreshes the window (`FUN_142deea90`) |
| `0x15` | `u32, raw` (`FUN_142deb010`) | adds ONE entry, then refreshes |
| `0x18` | `u32, u32, u8, raw` (`FUN_142deb620(mgr, pkt, 1)`) | adds one entry **and calls `FUN_1415aafa0(0x12)`** - a UI open. The best candidate for *"X wants to add you"*, which is the packet the owner never got. **[I]** on the meaning |

### An entry is 329 raw bytes

A manager entry is **0x149 bytes** - the stride in `FUN_142deb620`'s own search loop - and
`FUN_1402d4870` is two lines: `read_raw(packet, dest, 0x149)`. **[L]** So an entry goes over
the wire as a **fixed 329-byte blob copied straight into the struct**, exactly like this
project's party-member block: to send one, the 329 bytes have to be laid out correctly, and
the field meanings come from whoever reads `entry+N` afterwards rather than from the decoder.

Note that `0x19`'s rows are only `{u32 id, str name}` - it is the *list* of ids and names,
while `0x15`/`0x18` carry a whole entry. A list reply is therefore the cheaper thing to build
first, and it is what the window draws.

## 4. What is NOT known - and what each gap costs

The handler logs **every unmodelled sub-op with its number and the list's pending rows**, so
one click of the window's Accept button in one run names it.


* Every sub-op's meaning past `1` outbound, and past `0x19` inbound. **[I]** - 31 of the 34
  reply cases are undecoded.
* The **0x149-byte entry's fields** (`0x15` / `0x18` carry one). Not needed for `0x19`, which
  is ids and names only.
* Whether `0x00ED` (8 zero bytes, exactly once per client per session, also unanswered) is the
  list request. A candidate, nothing more.
* What `kind` values other than `7` do, and what the three `u32`s and the `str` in the reply
  are - `a` is presumably a character id and `name` the other party.

## 5. The popup, and both of its buttons - 2026-09-22

The owner: *"When someone sends a buddy request, there should not be any chat commands. Please use
the client's built in UI elements, there should be one similar pop up just like the party
invitation, chat invitation, or trade invitation."*

**The walk, all [L]:**

1. String `0x0438` is *"Friend request from"* - the exact parallel of the trade invite's
   caption. `FindConstArgCalls` on the string resolver puts its only real use in
   `FUN_1418099f0`, the balloon painter, under **`case 0xe: case 0xf:`** of the switch on
   `balloon+0x300` - the same field the trade invite's `0x15` selects.

## 6. The record, the crash, and what `0x19` really is - 2026-09-22

The owner: *"Adding someone as a friend causes a fatal client crash to whoever the invitation was
sent to."*

**The client named the packet, as it has four times before.** `world-ch0.log` 00:02:20.980:

```text
00:02:20.974 -> [Tester2#214] 0x00A7  1a00d7000000d7000000040057697370000000000000000000000000
00:02:20.980 <- [Tester2#214] 0x009E  0100 26000000 2200 | 90eb8eeb a700 <that body> | a700
00:02:24.011                  ch0 #2 ended: forcibly closed by the remote host
```

Class **1**, reason **`0x26`** - which `research/shop-packet-rejected.md` names exactly: *a
decoder asked for more bytes than the packet had left*. Length `0x22` = 34 = our 4-byte network
header plus the opcode plus 28 bytes of body, and `hi ^ lo` of `90eb 8eeb` is `0x1e` = 30, the
true packet length. Every field checks out; nothing is truncated. The client simply ran out of
our packet.

### The `0x1A` arm reads eight things, and this server sent seven

`FUN_142defd40` case `0x1a`, in order: `u8` flag, `u32`, `u32`, `str`, `u32`, `u32`, `u32` -
**28 bytes with the sub-op, which is exactly, to the byte, what this server built** - and then,
when `FUN_142deaf60` returns 0, `FUN_1402d4870(slot, pkt)`, which is
`read_raw(pkt, dest, 0x149)`. There was nothing left, so the first byte of that read threw.

`FUN_142deaf60` is worth naming because it is *not* a count: it compares the lengths of the
manager's first two parallel arrays and, when they differ, **sends `0x0193` sub-op 0** and
returns 1 - a "resend my friend list" request, and the reason the record read is conditional.
Both arrays were empty and equal, so the read happened.

### The 329 bytes, and the four things that pin them

Three offsets come from `FUN_142dec8f0`, which walks the loaded records with a `0x149` stride:

| evidence | offset |
|---|---|
| `uVar1 = *puVar9`, the id it hands the balloon | `0x00` `u32` |
| `puVar9 + 1` walked by an inline `strlen` | `0x04`, a C string |
| **`if (*(char *)((longlong)puVar9 + 0x11) == '\x01')`** - the test that decides to raise a request balloon at all | `0x11` `u8` |

Those three fix the name field at `4..0x11`, i.e. **13 bytes**. The fourth instrument is the
reference tree's `Friend.encode` - v214, a **different game version**, a candidate generator
and never a fact - which reads `int friendID, str13 name, byte flag, int channelID, str17
group, byte mobile, int friendAccountID, str13 nickname, str256 memo, int inShop`. It agrees
with all three measured offsets, and its `FriendFlag` enum is `Friend(0), FriendRequest(1),
FriendOffline(2), FriendOnline(3)` - so the literal `1` the client tests for is that enum's
`FriendRequest`. Four instruments, one layout:

```text
0x000  u32        character id            [L]
0x004  char[13]   name, NUL-terminated    [L]
0x011  u8         flag: 1 = a request     [L] on the test, [I] on the other values
0x012  u32        channel                 [I]
0x016  char[17]   group                   [I]
0x027  u8         mobile                  [I]
0x028  u32        account id              [I]
0x02C  char[13]   nickname                [I]
0x039  char[256]  memo                    [I]
0x139  u32        in shop                 [I]
0x13D  12 bytes   UNKNOWN - sent as zeros. The reference's fields add up to 317, 12 short of
                  329, and the same tree's invite carries level, job and subJob. That is a
                  guess and is labelled as one.
```

### `0x19` was never the list, and it was clearing the one that is

The `0x19` arm fills the `std::map` at `manager+0x18` with `{id, name}`, and **on the way there
it empties the record array at `manager+0x00` and zeroes the count beside it** - the array the
window strides over. So `0x19` is an id-to-name cache, and this server had been sending it as
the list on every field entry: the window was being handed an empty list on purpose.

The list is **sub-op `0x15`** (`FUN_142deb010`): `u32 count`, then `count * 0x149` bytes in a
**single** `read_raw`, then two resolved flags per record, then a window refresh. Its arm then
calls `FUN_142dec8f0`, which is the other caller of the kind-`0x0E` balloon setter - so the
client raises its own *"Friend request from"* popup for **every record whose `flag` is 1**,
without being asked. That is how the real server delivers an offline request.

This server now sends `0x19` **then** `0x15`, in that order, because the other order throws the
list away; only accepted friends are listed, with `flag` 3 or 2 from the roster (the hub when
one is linked, this channel's presence otherwise); and a waiting request stays an invitation -
the `0x1A` balloon, which now carries its record.

### What it cost to find, and what it would have cost to guess

Nothing on screen, and no client run: the rejection was already in the log the owner's run left
behind, and every address above came out of four Ghidra batches. The guess that would have been
wrong is the tempting one - that `0x1A` needed *four more bytes*, because the other three
archived `0x009E`s all have `length = packet + 4`. They do, and it means nothing: `0x22` is the
**length** field, not a position. The `0x009E` says the read ran out; it never says by how much.

## 7. The group report is a loop, and what the buddy list proved - 2026-09-22

The record works: the Buddy tab drew *"Default Group (1/1)"* with a NAME / JOB / LV row. Three
things came out of the same run.

### The loop

```text
00:44:04.315 <- 0x0193  14 01000000 01 0d00 "Default Group"     the window's group names
00:44:04.315 -> 0x00A7  0x19  the id-to-name map
00:44:04.315 -> 0x00A7  0x15  THE LIST, 1 record
00:44:04.316 <- 0x0193  14 01000000 01 0d00 "Default Group"     ... and again
```

**32 566 round trips, one per millisecond, a 42 MB log.** Both arms of a list reply end in a
window refresh (`FUN_142deea90`, `FUN_142debd10`), and a refreshed window hands its group names
back. Answering that with a list closes the ring. Sub-op `0x14` is a report - the same shape as
`0x013D` - and is answered with nothing.

The generalisation, which is this file's own rule in a new direction: **"always answer" is about
a request the UI is waiting on.** A packet the client emits *as a consequence of* a reply is not
one, and answering it is not caution, it is a cycle.

### The correction

Section 6 said `0x19` *empties the record array*. It does not. Re-read, the arm clears and
refills **its own `std::map` at `manager+0x18`** with the size at `+0x20`; the three parallel
record arrays at `+0x00`, `+0x08` and `+0x10` are untouched. `0x19` before `0x15` is a
preference, not a requirement.

### Case `0x2D` names three of the four unknown tail words

The blank JOB and LV columns are the 12 bytes at `0x13D`..`0x149` going out as zeros, and the
notify arm writes into exactly that region:

```text
u32  id            -> later stored at rec+0x00
u32  accountId
u8   ?
u32  channel
u8   hasDetail
u8   ?
  when hasDetail:
u32  count of records to match, then FUN_142debab0 finds the row
str  name          -> rec+0x04
u32                -> rec+0x139     -1 = leave unchanged
u32                -> rec+0x13D     -1 = leave unchanged
u32                -> rec+0x141     -1 = leave unchanged
```

It also reads `rec+0x2C` back as a C string, which is the reference's `nickname` at `0x2C` -
a fifth independent confirmation of the inferred layout. **[L]** on the offsets, **[I]** on
which of `0x139`/`0x13D`/`0x141` is level and which is job.

This one packet is what three of the owner's four open reports need: the location check
(*"the owner - Checking location"*), the logout that leaves a friend showing online, and the two
blank columns.
