## 3. Which restores it applies to

| question | answer | label |
|---|---|---|
| flat (`hp`/`mp`) terms? | yes | **[I]** |
| percentage (`hpR`/`mpR`) terms? | yes | **[I]** |
| does the HP skill bonus MP, or the MP skill HP? | **no** | **[L]** |
| before or after the missing-HP cap? | **before** | **[D]** |

### 3.1 The pool split is [L], and it is not hypothetical

*"Improved **MP** Recovery … increases **MP** recovery from items"* names the pool twice, and
the HP twin names HP in the same two places. **Seven of this client's 44 consumables restore
both pools** - `2000004`, `2000005` (Elixir, `hpR 100 / mpR 100`), `2010006`, `2020002`,
`2020011`, `2020018`, `2020019`. **[L]** So a Magician drinking an Elixir must get the bonus
on the MP half and not the HP half, and that is a difference somebody can see.

`each_skill_bonuses_its_own_pool_and_only_its_own` asserts both directions, because a
one-directional test passes on a function that bonuses everything.

### 3.2 Flat-vs-percentage is [I] because **nothing in this client can disagree**

The tooltip names the pool and the source and does not name a term. So the question is
whether to bonus the total or each term - and:

> **No item in `gm-handbook/consumables.txt` carries both a flat and a percentage term on the
> same pool.** 0 of 44 for HP, 0 of 44 for MP. **[L]**, both directions counted by
> `nothing_in_this_client_can_tell_the_two_bonus_orders_apart`.

The two readings therefore produce identical numbers on every item this client has, and the
choice is **unobservable**. That is why it is labelled [I] rather than quietly presented as a
finding. The total is bonused, because that is the number the item's own tooltip promises the
player and the one `Restores::hp_for` already returns.

If a future WZ adds an item with both terms on one pool, that test fails and says so - which
is the point of writing the negative down as a test rather than as a sentence.

### 3.3 The cap comes after the bonus

`consume.rs` caps the gain at what is missing. The bonus goes **before** that cap, because
capping first and multiplying second would let a near-full drink overshoot the maximum, and a
number above the maximum in the HP field is what the client draws as a bar past its own end.
`Restored::capped` does the cap, so the wiring cannot forget it - `CLAUDE.md`'s Heena rule
that an effect hanging off a separate step is the one that gets missed.

`the_bonus_is_applied_before_the_cap_and_that_is_visible` uses a character missing exactly
220 MP: cap-then-bonus and bonus-then-cap disagree there (200 vs 220), so the test
discriminates rather than merely passing.

## 4. Rounding: floor. **[I]**

`boosted(amount, percent) = amount * (100 + percent) / 100` in `u64`, truncated.

Three reasons, in the order they mattered:

1. **It is what every other percentage in this repo already does.**
   `consumables::Restores::hp_for` is `max_hp * hp_percent / 100`.
   `session::combat::on_user_hit`'s Magic Guard split is
   `u64::from(applied) * u64::from(guard_percent) / 100`. A fourth rounding rule in a fourth
   place is how two of them end up disagreeing.
2. **Floor can never pay more than the tooltip promises.** Round-half-up can, by one point.
3. **A future reader who "simplifies" this back to integer division gets the same answer.**

### 4.1 What floor costs, measured rather than assumed

The brief warned that *"a 20% bonus on 10 MP is where an off-by-one lives"*. It does - `10`
at level 1 is `floor(10.5) = 10`, so level 1 would add nothing to a 10-point item. **But this
client has no 10-point item.** Enumerated over the generated table:

```text
flat MP amounts in gm-handbook/consumables.txt:
  30 50 100 150 200 300 450 800 900 1500 2000 2500
flat HP amounts:
  30 40 50 60 100 120 150 160 250 300 360 500 600 800 1000 1500 2000 2500

smallest case: floor(30 * 105 / 100) = 31          <- level 1 on the smallest item still pays
```

**Across every (real item, level 1..=15) pair there is no case where the bonus rounds away to
nothing.** **[L]** - `no_real_item_at_any_level_gets_a_bonus_that_rounds_to_nothing` is that
enumeration against the file, with a `checked > 100` control so an empty sweep cannot pass as
a clean one. `the_bonus_rounds_down` still pins the `10 -> 10` case explicitly, so the choice
is written down rather than left to integer division to decide quietly.

### 4.2 The one place the choice is visible, and it is pinned

A **percentage** restore floors twice - once in `Restores::mp_for`, once in `boosted`:

```text
max MP 237, an item with mpR 35, skill level 15 (y = 20)
  floor(237 * 35 / 100)        = 82     <- Restores::mp_for
  floor(82 * 120 / 100)        = 98     <- what the player gets
  floor(237 * 35 * 120 / 10000) = 99    <- what one fused multiply would give
```

One point. The module composes with `Restores` rather than reimplementing it, so the base
amount has exactly one definition, and `a_percentage_restore_floors_twice_and_that_is_deliberate`
pins the 98 so the choice cannot drift by accident.

Four of the 44 items carry `mpR` and three carry `hpR`, so this is a live path and not a
hypothetical.

## 5. Why the level table is hard-coded when `skilltable` already parses `y`

Because **a missing `gm-handbook/` must not silently switch the bonus off.**

`SkillTable::load` answers an *empty table* for a missing file, by design. A `bonus_percent`
that read `y` at runtime would then return `0` at every level: a running server, a learned
skill, and a passive that does nothing - which is the exact screen this module exists to
remove. `Config::map_exists` was fail-open in the same way for a day, and
`session::consume::use_return_scroll` now refuses loudly rather than inheriting it.

So `ITEM_BONUS_PERCENT` is the runtime source and `bonus_percent_from_wz` exists **only** so a
test can prove the two agree. `CLAUDE.md`: *a constant that came from reading data is a claim,
not a fact - assert it against something that can disagree.*

`crates/world/src/itemrecovery.rs` is built, tested and **not wired**. Nothing calls it. Its

### The change: `crates/world/src/session/consume.rs`, `Session::on_use_item`

**Replace lines 80-81:**

```rust
        let hp_gain = restores.hp_for(chr.max_hp).min(chr.max_hp.saturating_sub(chr.hp));
        let mp_gain = restores.mp_for(chr.max_mp).min(chr.max_mp.saturating_sub(chr.mp));
```

**with:**

```rust
        // **Improved HP/MP Recovery.** The owner, 2026-08-30. `restored` folds each skill's `y`
        // into its OWN pool and `capped` still caps at what is missing - the bonus goes in
        // before the cap, or a near-full drink could overshoot the maximum.
        let learned = crate::itemrecovery::Learned {
            improved_hp_recovery: self
                .store
                .skill_level(chr.id, crate::itemrecovery::IMPROVED_HP_RECOVERY)
                .unwrap_or(0),
            improved_mp_recovery: self
                .store
                .skill_level(chr.id, crate::itemrecovery::IMPROVED_MP_RECOVERY)
                .unwrap_or(0),
        };
        let gained = crate::itemrecovery::restored(&restores, chr.max_hp, chr.max_mp, learned);
        let (hp_gain, mp_gain) = gained.capped(chr.hp, chr.max_hp, chr.mp, chr.max_mp);
```

the `0x007C` still carries the absolute totals.

`Store::skill_level` **returns `Ok(0)` for a skill the character never raised**, not an error,
so `unwrap_or(0)` is only reached on a real database failure - and there it degrades to the
current behaviour rather than refusing the item. `CLAUDE.md`'s *always answer*: this path is
latched, and a refusal costs not one potion but every later use in the session.

### And add the bonus to the log line, lines 120-123

The log line is the only place a run can show that the bonus fired. Append to the `what`
string, or the next capture cannot tell "the skill applied 0%" from "the wiring is absent" -
