# Chairs: `0x00DB` sits, `0x00DA` asks to stand, and nothing we send releases one

The owner, 2026-09-08, on a live client: *"my character just sat in a chair, but the idle recovery
did not adjust to match the chair's recovery stats."* Then, minutes later: *"I also cannot get
out of the chair, the server won't let me."*

Tags: **[L]** read off this client's listing or a capture, **[D]** derived, **[I]** inferred.

---

## 1. The two opcodes, from the capture of that session

```text
02:54:41.004 <- 0x00DB  25 bytes
804a5d05 d5ed2d00 04000000 00 ffffffff fd000000 2c050000
 tick     3010005  slot 4

02:55:03.328 <- 0x00DA   2 bytes   ffff
```

`0x2DEDD5` is **3010005**, which `gm-handbook/items.txt` names **Red Chair** - the chair the owner
said they sat on - and the `4` behind it is its slot in their Set Up tab, which is where the
screenshot shows it. **Two independent values agreeing with a screen** [L].

`0x00DA`'s `0xFFFF` is written as an immediate by `FUN_142cd3a60` (`mov edx, 0xffff` at
`0x142cd3add`) [L], so the `u16` is a chair id and `-1` means *none*.

The client chooses between them: `call 0x14183ac00 / test eax,eax / jle` at `0x1428b5f0b` -
a positive result sends `0x00DB` through `FUN_142cd2e20`, otherwise `0x00DA` [L].

## 2. Both latch, and that decides how they must be answered

`0x00DA` and `0x00DB` are both in `net::dropmoney::LATCHING_REQUESTS`, and their builders open
with the same two guards [L]:

```text
142cd3a84  cmp dword ptr [rcx + 0x2338], 0 / jne return
142cd3a91  cmp dword ptr [rcx + 0x2330], 0 / jne return   <- the exclusive-request latch
142cd3abe  call 0x1429e3ef0 / sub eax,[rbx+0x2334] / cmp eax,edi / jl return   <- a rate limit
```

So an unanswered sit would leave the client **unable even to ask to stand**, on top of freezing
every later inventory action. Both handlers keep sending the empty-mask `StatChanged` unlock the
catch-all arm used to send; `session/chair.rs` says so and a test asserts it.

## 3. What each chair restores

`Item/Install/Install_000.wz` -> `0301.img`, 11 chairs, every scalar under `info` counted [L]:

```text
price 11/11   slotMax 11/11   recoveryHP 10/11   reqLevel 8/11
tradeBlock 6/11   notSale 3/11   recoveryMP 3/11
```

| id | name | HP | MP | lev |
|---|---|---|---|---|
| 3010000-3010002 | The Green/Yellow/Red Relaxer | 30 | - | - |
| 3010003-3010006 | Sky-blue / Green / **Red** / Yellow Chair | 30 | - | 5 |
| 3010007 | Pink Seal Cushion | 30 | - | 0 |
| **3010008** | **Blue Seal Cushion** | **-** | **10** | 0 |
| 3010009, 3010010 | Henesys / Kerning City Resident's Chair | 20 | 5 | 10 |

**`recoveryHP` is absent on the Blue Seal Cushion and that absence is the data.** A reader that
defaulted a missing figure to the common 30 would invent HP regeneration for a chair the client
says gives none. `tools/dump_chairs.py` writes the 0 explicitly and a test pins it.

**The unit is per tick, and it is measured rather than assumed.** The Red Chair's own tooltip
reads *"Restores an additional 30 HP every 10 seconds"* - *additional*, so it adds to the flat
base, and 10 000 ms is exactly `regen::REGEN_EVERY_MS`. Both halves off the client.

`research/mp-regen.md` §5.1 had recorded the gap - *"This server has no chairs"* - and named
`userpool.rs:776` sending the chair item id as a literal `0`. That is still true of the remote
record; this change is about the idle tick only.

## 4. The half that is NOT fixed: you cannot stand up

The owner's client sent **eight** `0x00DA` bodies of `ffff` across four minutes and stayed seated [L].
So the latch is not the blocker - we answer it every time, which is why they could keep retrying -
and **the client leaves a chair only when the server sends something we do not send.**

What was eliminated, so the next pass does not repeat it:

* **Inbound `0x00DA` is not the echo.** There *is* a handler at that number in the client's
  gamestage table (`FUN_142cde3c0`), but it decodes a `u32` and runs a bitmask loop - not a
  chair [L].
* **`FUN_14183ac00` is not the chair-state accessor.** It is an array indexer: it takes an
  index, bounds-checks it against a length at `[array-8]`, and returns the element [L]. The
  chair id it yields comes from whatever array is passed in.
* **The caller chain from the builders does not reach a setter** in the two passes tried.

The chair *does* appear in the remote-user record - `net::userpool` writes a `u32` chair item id
at body offset 418 and a `u8` "no chair to decode" at 435, both hard-coded to absent [L]. **[I]**
that the release is a small user-pool broadcast rather than a reply to `0x00DA`, on the strength
of the state living in that record; that is a candidate, not a finding, and the honest next step
is to find the handler that writes those two fields on a *remote* user and work back to the
opcode - the same method that found the keymap's `0x05F1`.

Until then `session/chair.rs` clears the seated state when the player asks to stand, so the
recovery bonus stops immediately, and the character stays seated on screen.

## 6. The release opcode: NOT FOUND. What was established and what was eliminated

The owner asked for this before the next run. **I did not find it.** What follows is so the next
attempt starts where this one stopped rather than repeating it.

### 6.1 The field and its two accessors are now named [L]

`research/0x0224-remote-user-first-use-fault.md` already had the field; this pass added the
setter by reading the vtable around it.

| | |
|---|---|
| `CUser + 0x3c28` | the chair id. `-1` is **not sitting**; the client's own initialiser writes that literal at `0x142769d49` |
| `FUN_142834020` | `IsSitting` - `(m_0x3c18 && FUN_141716a90(m_0x3c18)) \|\| m_0x3c28 != -1`. **Vtable slot 36**, `+0x120` |
| **`FUN_1428341a0`** | **`SetChair(CUser*, int)`** - `mov dword ptr [rcx + 0x3c28], edx ; ret`, two instructions. **Vtable slot 38**, `+0x130` |

Both are virtual and have **zero direct callers**, which is why `callers.py` finds nothing and
why the first pass stalled.

### 6.2 The inbound `0x00DA` handler is NOT the release [L]

`FUN_142cde3c0` (the client's inbound `0x00DA`) does call `[rax + 0x130]`, at `0x142cde706`,
and for a while that looked like the answer. It is not:

```
142cde700  mov rax, qword ptr [r14]
142cde703  mov rcx, r14
142cde706  call qword ptr [rax + 0x130]     <- no EDX is set anywhere before it
142cde70d  mov rdx, qword ptr [r14 + 0x20]
142cde715  cmp rax, 0xffffe
```

`SetChair` takes its value in `EDX` and nothing loads `EDX`; the `this` is then used as a
container. **Slot 38 belongs to many classes, and this is a different class's slot 38.**

### 6.3 Why the virtual-dispatch route did not converge

* `call [reg + 0x130]` appears **372** times in `.text`.
* Requiring the containing function to also call a decode primitive leaves **59**.
* Requiring an `EDX` load after the last preceding `call` leaves **87** of the 372.
* Cross-referencing against the inbound opcode table leaves nine, of which `0x00DA` is
  eliminated above and the rest are Family / Expedition / Memo handlers.

None of these filters can tell a `CUser`'s slot 38 from any other class's, and that is the gap.

### 6.4 An instrument that lied, caught by its own control

A byte scan for writers of the sibling latch `ctx+0x2338` first reported **0 writes** - and
reported **0** for `ctx+0x2330` too, which `research/` proves is written at `0x142d547bb`. The
ModRM mask was `& 0xC7`, which pins the register field to `rax`. Corrected to `& 0xC0`, the
control returns 62 writes and `+0x2338` returns 6. **The negative was a property of the scan.**
Recorded because the same mask error would silently break any future field scan written the
same way.

### 6.5 The two next steps, in order of cost

1. **`python tools/fieldrefs.py 0x3c28 --write`** - the instrument built for exactly this
   question, and it resyncs where a linear sweep desyncs. The earlier claim that *"nothing
   overwrites `+0x3c28` after Init"* came from `rangescan.py`, which has the `mob+0x42c` blind
   spot: a store through a `lea`'d pointer is invisible to it. A third writer is the answer.
   This sweep was started and had not finished.
2. **Read `+0x3c28` out of a live, seated client.** The owner's client had them stuck in a chair; it
   has since closed, so the chance was missed. Next time it happens, that one `u32` splits the
   question in half: **`3010005` means the client set its own chair locally** and the stand path
   is something we are blocking, while **`-1` means the client never considered itself seated**
   and the sprite is cosmetic - which would make "the server won't let me out" a different bug
   entirely. `tools/keymapdump.py` is the read-only pattern to copy.

### 6.6 Step 1 was run. It closes the field question and does NOT give the opcode.

A displacement scan for writers of `CUser+0x3c28`, with the corrected ModRM mask and a control
that returns **62** writes for `ctx+0x2330`, finds **five** [L] - three more than the earlier
`rangescan.py` pass reported. All three extra ones are false positives, and each was read:

| site | what it really is |
|---|---|
| `0x14089f12b` | the **ZtlSecure encoder**: PRNG key to `+0x3c28`, `key^value` to `+0x3c2c`, checksum to `+0x3c30` from `0xbaadf00d` - the same scheme `net::opcode` documents for equip stats. A different class with a secure slot at that offset. |
| `0x1403cda61` | inside a 26 KB function, the same unrolled-copy shape as below |
| `0x14294d285` (this one is `+0x3c18`) | an **unrolled struct copy**, `+0x3bd4` through `+0x3c30` field by field |

So the earlier conclusion survives a better instrument: **the only real writers of the field are
the `0x0224` decoder, the `-1` initialiser, and `SetChair` itself.** A release therefore has to
go through `SetChair`, which is virtual, and no static filter available here separates a
`CUser`'s slot 38 from the 372 other `call [reg+0x130]` sites.

**The remaining step is the live read, and it needs a seated client** (§6.5 item 2). Static
analysis has been taken as far as it goes without type information.

## 7. MEASURED 2026-09-09: it is not a chair bug. `IsSitting` is true from login.

The owner got stuck again, and this time the client stayed open. `tools/chairprobe.py` walks
`*0x143AA84A0 -> +0x2358 -> CUser` and reads both halves of `IsSitting`. Both controls passed,
and one of them is strong: the session pointer it read matched the object the **hook log was
printing at that moment** - a check from a different instrument on the same live process.

```
local CUser = 0x56bea050
  CUser + 0x3c18  (chair OBJECT ptr) = 0x0
  CUser + 0x3c28  (chair ID)         = 0
```

**Zero is neither registered outcome.** Not the client's own absent form (`-1`, written by its
initialiser at `0x142769d49`), and not the Red Chair id `3010005` they were sitting on. And
`IsSitting` is `(obj && ...) || m_0x3c28 != -1`, so **zero makes it unconditionally true**.

### The discriminator, settled from the log rather than by asking

The second probe was run after a relog and before touching a chair, and `world.log` proves the
ordering [L]:

```
03:52:17  0x007D + SetField        first login
03:53:13  0x00DB  d5ed2d00         sat on the Red Chair (3010005)
03:53:58  0x00DA x4                stand attempts
03:58:24  0x007D + SetField        RELOGGED
(no 0x00DB after)                  and the probe read 0 here
```

**The field is 0 from login, before any chair exists.** So `IsSitting` has been true since the
moment the character entered the field, in every session, and "cannot get out of the chair" is
not a missing release packet: there is no seated state to leave. Every hour spent hunting a
release opcode in §6 was aimed at the wrong question, and this one measurement retires it.

### What wrote the zero

Only three things write `+0x3c28`: the `-1` initialiser, the `0x0224` decoder (from body offset
416), and `SetChair`. **The `0x0224` decoder is excluded**: `user_enter_field` is only built in
`session/multiplayer.rs`'s spawn path, for *other* players, and the owner was alone - no `0x0224` was
sent at all [L]. The initialiser writes `-1`. So **`SetChair(0)` is called during login**, and
the value is 0 because whatever it was handed was 0.

### The archive cannot corroborate this, and that is a property of the archive

The same pointer walk over all 38 dumps returns freed-memory fills for many of them -
`0xdddddddddddddddd` at `+0x3c18`, `0xff9b6e0fffa37611`, `-572662307` - so the session and user
objects do not survive intact in a *crash* dump. The dumps that do walk cleanly all read 0, but
that cannot be separated from "the walk landed on something dead". **Not used as evidence
either way.** `research/0x0224-remote-user-first-use-fault.md` reports `-1` for the local user
in four dumps, reached by a different route (the faulting function's `param_1`); the two
disagree and the live reading is the one with a passing external control.

### The next step

Find the login-path call to `SetChair`. It is virtual (slot 38), so the displacement scans in
§6 cannot see it; what changed is that the *caller* is now known to run during field entry
rather than on a chair click, which is a far smaller search than 372 sites across the image.

**And it is worth checking what else gates on `IsSitting`**, because if the client has believed
it is sitting since login in every session this project has ever run, that flag is an input to
more than chairs.

## 10. SETTLED 2026-09-09: the chair id is not involved. The state is the OBJECT at `+0x3c18`.

The same probe, same client, same session - once standing and once sitting [L]:

| | `+0x3c28` id | `+0x3c18` obj | `FUN_141716a90(obj)` | checksum | `IsSitting` |
|---|---|---|---|---|---|
| **standing** | `-1` | `0x5982a08` | **0** | VALID | **FALSE** |
| **sitting** | `-1` | `0x5558d5e0` | **1** | VALID | **TRUE** |

**Sitting does not touch `+0x3c28` at all.** It stays at the absent value in both states. The
entire seated state is the object at `+0x3c18` and the ZtlSecure boolean inside it, and the
checksum validates in both readings, so this is that structure and not a coincidence.

### What this retires

**`SetChair` is irrelevant to this bug.** `FUN_1428341a0` writes `+0x3c28`, the field that never
changes when a player sits on a Set Up chair. §6 spent 372 virtual call sites, four filters and
a client death hunting its caller, and §8's watch - the one that crashed the run - was armed on
it. All of that was aimed at the wrong field. The id path presumably serves map chairs or the
portable/miniroom case, which is what the two-clause `IsSitting` is for.

**The release must clear the flag in the `+0x3c18` object**, not write `-1` anywhere.

### The next step, and it is small now

The object is the state, so the class that owns it is the target, and its vtable names it. The
probe now prints the chair object's vtable and header. From there:

1. Look the vtable up in `.rdata`, find its slot count and the code that `lea`s it - that names
   the constructor and the class's code region.
2. The method that writes the secure flag at `obj+0x40..0x47` is the setter; the release is
   whoever calls it with 0. That is a *one-class* search, not an image-wide one.

Also worth noting: the object pointer **differs between the two readings** (`0x5982a08` vs
`0x5558d5e0`), so a chair is not one long-lived object being toggled - a new one appears. That
is consistent with the flag being per-chair rather than a single "am I seated" bit, and it means
the release may be a destruction rather than a clear.


### 10.1 The class is named, and the setter is a two-branch attach/detach

The chair object's vtable is **`0x1433CEF78`** [L], read live. `tools/xref.py --va` finds
**one** `lea` for it: `0x141714c4f`, inside `FUN_141712040`. So the class's code is the
`0x1417xxxxx` region - the same neighbourhood as `FUN_141716a90`, its secure getter.

Eight direct calls to the byte PRNG `0x1407386b0` live in that region, and three functions
write the secure slot at `+0x40/+0x41/+0x44`:

| function | writes | reading |
|---|---|---|
| `FUN_141716190` | `[rdi+0x40], al` and `[rdi+0x41], **al**` | **constructor** - same register into both bytes, so the value is `al ^ al` = **0**. It also writes a vtable (`0x1433CED98`, a sibling class) |
| `FUN_1417164c0` | `[rsi+0x40], al` and `[rsi+0x41], **al**` | same shape, value **0** |
| **`FUN_1417165e0`** | `[rsi+0x40], **al**` and `[rsi+0x41], **dl**` | **the setter** - different registers, so a variable value |

`FUN_1417165e0(rcx = obj, rdx = ptr)` opens with two virtual calls (`vtable+0x68`,
`vtable+0x70`) and then `test r15, r15 / je 0x141716712` - a **null second argument takes the
other branch** [L]. That is an attach/detach pair, and the release is the detach.

### 10.2 A workaround is now precisely specified, if it is ever wanted

The encoding is fully known, so the flag can be cleared without finding the packet at all:

```
key    = byte[obj+0x40]                      (leave as is)
byte[obj+0x41] = key                          -> value becomes key ^ key = 0
dword[obj+0x44] = ror32(key ^ 0xBAADF00D, 5) + key
```

The hook already writes client memory for the sentry's header repair, so it could clear the
flag on demand. **It is a workaround and should be labelled one**: it patches the client's
state rather than sending what a real server sends, and it would mask the real defect from
every later measurement. Recorded because it is now exact, not because it is recommended.

### 10.3 What is left

Find what drives `FUN_1417165e0` with a null second argument, or what destroys the object. That
is a one-class search in `0x1417xxxxx` rather than an image-wide one, and the field to watch is
known. **Do not arm a `watch@` to do it** - §8: two client deaths, the second with a single
watch and no guard page.

## 11. The client waits for us. Read three ways, and the sit is purely local.

### 11.1 Standing sends and waits - it never clears the chair itself

The tail of `FUN_142cd3a60`, after it writes `0x00DA`/`0xFFFF` [L]:

```
142cd3af6  mov dword ptr [rbx + 0x2330], 1     ; RE-ARM the exclusive-request latch
142cd3b05  mov dword ptr [rbx + 0x2334], eax   ; stamp the retry timer
142cd3b2e  mov eax, 1                          ; return "request sent"
```

**Nothing clears the chair.** And its caller `FUN_14187f150` is the same shape [L]:

```
14187f245  call qword ptr [rax + 0x120]   ; IsSitting()
14187f24d  je   skip                      ; not sitting -> do nothing
14187f258  call 0x142cd3a60               ; sitting -> ask the server
14187f25d  ret                            ; and that is all it does
```

So a reply is genuinely required. Our empty-mask unlock clears `+0x2330`, which is exactly why
eight retries went out instead of one - the client could ask again, and never got an answer that
meant anything.

### 11.2 Sitting needs no server at all

`FUN_1428d72e0` constructs the chair object, and one of its two callers is **`0x142cd2e20` - the
`0x00DB` sit builder** [L]. The client builds the object itself as it sends the packet. That is
why sitting works against a server that does nothing, and it is the asymmetry that makes this
bug what it is: **the client seats itself and asks permission to stand.**

### 11.3 A concrete gain: the local user has a global

`FUN_14187f150` does `mov rcx,[rip+0x22292d6] ; mov rax,[rcx] ; call [rax+0x120]` - it loads a
global, takes the object's vtable and calls slot 36, `IsSitting`. So **`0x143AA8518` holds a
pointer to the local `CUser`**, from the client's own code [L]. The session object the hook
watches, `0x143AA84A0`, is its neighbour - which is why a guessed offset from the session looked
plausible and was wrong twice.

`tools/chairprobe.py` now reads that global first and only falls back to searching. The vtable
control still applies, so a wrong anchor is caught rather than reported.

### 11.4 Still not found: the reply

Seven functions construct the chair object; none is an opcode handler in
`research/msexe-gamestage-opcodes.md`, and neither is anything one level above them. The table
does not cover the user-pool paths, so that is a gap in the map rather than a proof of absence.

**The cheapest remaining route is the one `probe.rs` was built for and it is not a `watch@`:**
its walk mode `<from>-<to>@<VA>` calls every inbound handler directly with a captured body and
uses an `int3` on a chosen function as the oracle. Point the oracle at whatever destroys the
chair object - the class's vtable slot 0 - and one launch names the opcode. That is a different
mechanism from the watch that killed two clients (it is the tool's designed path, and it is how
`0x0032` was found), but it deserves its own careful run and not a shared one.

## 12. FOUND: the reply is `0x0318`, and a release is TWO ZERO WORDS

The owner: *"the server needs to relay that action to all of the players in the map so other players
can see you sitting in a specific chair ID as well."* That is the right frame, and it is what
the client is waiting for.

### 12.1 The chain, each link read

```
CField::OnPacket  FUN_141820080
  141821e24  lea eax,[r9-0x224] / cmp eax,0x17b / ja      ->  opcodes 0x0224..0x039F
  141821e3c  call 0x1429b9300                             ->  CUserPool::OnPacket
      1429b93f2  mov edx,ebx / mov r8,rsi / call 0x14289a3a0  ->  the LOCAL user's OnPacket
          jump table 0x14289d660, index = opcode - 0x2C5, 218 entries
          index 83  ->  0x14289b8be
```

`0x2C5 + 83` = **`0x0318`** [L].

**The base and table are checked against two answers this repo established for other reasons**:
index `0x50` of the same table is `0x0315`, the revive dialog (`net::revive`), and index `0xC`
is `0x02D1`, the level-up effect (`research/level-up.md`). Neither has anything to do with
chairs, so the arithmetic is verified rather than asserted.

### 12.2 The body, and the arm that would have looked like the bug

```
14289b8c1  Decode4 -> chairId
14289b8cb  Decode4 -> second
14289b8d2  test chairId, chairId
14289b8d4  jne  -> 14289b904   mov r8d,chairId ; call 0x141712040   CONSTRUCT THE CHAIR  (SIT)
14289b8d6  test second, second
14289b8d8  je   -> 14289b8f1
14289b8da  call GetTick ; lea ecx,[rax+second] ; mov [r15+0x4898],ecx ; jne done   COOLDOWN, NO RELEASE
14289b8f1  mov rax,[r15] ; xor edx,edx ; call [rax+0xb8]                            RELEASE
```

| body | effect |
|---|---|
| `chairId != 0` | seat the player on that chair |
| `chairId == 0`, `second != 0` | **sets a cooldown and returns still seated** |
| `chairId == 0`, `second == 0` | **stand up** |

**The middle arm is a trap worth naming.** A release built as "chair id zero" with anything at
all in the second field leaves the player seated - indistinguishable on screen from the bug
being fixed, and it would have read as "the opcode is wrong". `net::chair::user_sit(None)`
sends both words zero and a test pins it.

### 12.3 What was wired

`net::chair::USER_SIT` = `0x0318` and `user_sit(Option<u32>)`. Both handlers now answer:
`0x00DB` echoes the seat, `0x00DA` sends the release. **Both still send the exclusive-request
unlock first** - the client's stand builder refuses to send while `ctx+0x2330` is set, so
dropping it would make a player unable even to ask.

### 12.4 Honest limits

* **Not yet seen on a screen.** Every step is read off the listing and the arithmetic is
  double-controlled, but no client has stood up yet.
* **This is the LOCAL user's opcode only.** `0x2C5..0x39E` dispatches to
  `ctx->localUser`, so `0x0318` seats the player who sent the request. **Other players in the
  map will still not see it** - the owner's actual requirement - and the remote equivalent lives in
  the `0x0224..0x02C4` half of the same range, which has not been walked. Named as unfinished
  rather than quietly half-done.
* Nothing authenticates: the chair id is not checked against the player's inventory.

## 13. `0x00DA` is TWO requests, and map chairs are the second one

The owner, 2026-09-09, after `0x0318` landed: *"sitting in chairs and then standing now works, but I
still cannot sit down in chairs that are present in the maps themselves, such as Henesys."*

The log says why, and it is the same shape as the `0x00D1` split this repo already carries
(*"two different requests and only the LENGTH separates them"*) - except here it is the value:

```
04:46:16.752 <- 0x00DA  2 byte body ffff     stand up
04:46:41.457 <- 0x00DA  2 byte body 1800     seat index 24 - a MAP chair
... six more, all 1800, all unanswered
```

`0xFFFF` is the absence of a chair; **a real index is a request to sit on map chair N** [L].
`net::chair::parse_cancel` already returned `Some(Some(id))` for that case and the handler
logged *"never seen before, not acted on"* - which was true, and was the bug.

### 13.1 The reply is a hypothesis, and it is labelled one in the code

`0x0318` is the **only** chair opcode the local user's dispatcher has: `FUN_14289a3a0`'s
218-entry table contains exactly one arm that touches a chair (index 83), and scanning that
whole function for `call [reg+0xb8]` - `SetSeat`, the method that writes the seat index through
`SetChair` - finds **one** site, inside that same arm, on the release path [L]. There is no
seat-index path in the dispatcher at all.

So either the index rides `0x0318`'s first field, or the map-chair reply lives outside that
dispatcher. The handler now sends the first, clearly marked untested in both the code and the
packet's log line. **It risks nothing already held**: today the client gets the unlock and
stays standing, which is exactly the failure the reply might fix.

Reading the next run: the player sits on the bench -> confirmed. Nothing happens -> map chairs
are not this opcode and the search moves outside the local user's table.

### 13.2 Two things learned on the way, worth keeping

* **`SetSeat` (`FUN_1428a81d0`, vtable slot 23 / `+0xb8`) ends by sending `0x00DC`** -
  `mov edx,0xdc / COutPacket / SendPacket` right after `SetChair(-1)` [L]. That is why the
  watch's `called-from` was `0x1428a8324`: it is the instruction after the `SetChair` call.
  It also means leaving a seat makes the client re-announce field entry.
* **`FUN_1428a9f20` is an out-of-line duplicate of the `0x0318` arm** - same two `Decode4`,
  same three-way branch, same `SetSeat(0)` release. It looked like a second chair handler and
  is not one; the same trap `net::revive` records for `FUN_142903cd0`.

## 14. `0x0318` REFUTED for map chairs; the remote opcode is `0x02AD`

The §13 hypothesis was tested and is **wrong**. The log shows the reply going out and the
client ignoring it [L]:

```
04:55:26.044 <- 0x00DA 1800            seat 24
04:55:26.045 -> 0x0318 (seat as chair id)
04:55:26.614 <- 0x00DA 1800            retried
04:55:27.244 <- 0x00DA 1800            retried
04:55:27.834 <- 0x00DA 1800            retried
```

Four replies, four retries, no sit. **A clean negative**, and it eliminates the local user's
dispatcher: `FUN_14289a3a0` has one chair arm out of 218 and its only `SetSeat` call is on the
release path, so there is no seat-index path in it to have missed.

### 14.1 The pool splits five ways, and the fourth is the chair

`FUN_1429b9300` [L]:

```
opcode == 0x224                -> 0x1429b9467
opcode == 0x225                -> 0x1429b944d
opcode - 0x226 <= 0x6c         -> FUN_1429bafb0     (0x0226..0x0292)
opcode - 0x293 <= 0x31         -> FUN_1429bb720     (0x0293..0x02C4)
opcode - 0x2C5 <= 0xd9         -> the LOCAL user    (0x02C5..0x039E)
```

`FUN_1429bb720` decodes a **character id**, looks the user up, then uses a byte-indexed table:

```
1429bbb10  add   esi, 0xfffffd6d              ; index = opcode - 0x293
1429bbb22  movzx eax, byte [0x1429bbd10 + index]
1429bbb2b  mov   ecx, dword [0x1429bbcd0 + eax*4]
```

Dword slot 2 is `FUN_1429d4fd0`, which constructs a chair object, and the byte table maps that
slot from exactly **one** opcode: **`0x02AD`** [L]. `0x02AE` reaches `FUN_1429d5290`.

Body: `u32 characterId, u32 chairId, u32` - the pool consumes the id, the handler reads two
more, and `0x1406e8f00` is a bare `jmp` to `Decode4` so both are 32-bit [L].

### 14.2 This is also the relay the owner asked for

*"the server needs to relay that action to all of the players in the map so other players can
see you sitting in a specific chair ID as well."* `0x0318` carries no character id and the
local dispatcher applies it to `ctx->localUser`, so it can only ever seat the receiver.
`0x02AD` names the character, which is what a broadcast needs. `session/chair.rs` now publishes
it on **all three** transitions - Set Up sit, map-chair sit, and stand - superseding on the
character id so a second sit replaces the first rather than queueing behind it.

### 14.3 Status

* Set Up chairs: sit and stand **confirmed on a screen**.
* Map chairs: `0x02AD` is sent to the player and to the map. **Untested.**
* Other players seeing it: sent, **untested** - it needs two clients on one map.

## 15. `0x02AD` KILLED A CLIENT: the body was one byte short

The owner, 2026-09-09: *"Tester2's client actually exited when Cobalt is sitting in a chair."* The
two logs pin it to the millisecond [L]:

```
world.log       05:27:38.247 -> 0x02AD UserSitRemote: character 213 sat on chair/seat 3010005
hook log        01:27:38.252 ***** CLIENT FAULT #1: code=0xc0000005 at 0x140ce89d6 ...
                             30 C++ throw(s) seen before this *****
```

**Five milliseconds.** The packet is mine, added the same evening, and it is the third time in
this project's history that a short body has killed a client.

### 15.1 The cause, and it is the exact failure `CLAUDE.md` warns about

The body was built from the **first 26 instructions** of `FUN_1429d4fd0` - two `Decode4` after
the pool consumes the character id - and the function is 658 bytes. `tools/reads.py`, which
exists *because* a truncated packet killed the client twice before, counts **three** reads:

```
FUN_1429d4fd0  0x1429d4fd0..0x1429d5262 (658 bytes)  depth 3
  0x1429d4ff7  READ u32 (direct)
  0x1429d5001  READ u32 (direct)
  0x1429d50e8  READ u8  (direct)  gated?
```

The third is **260 bytes further in** than anything I had read. A 12-byte body made the
client's `Decode1` underflow, and this client's decoders answer underflow with a C++ throw -
which is why the fault line counts 30 of them.

**I had the right instrument and did not run it.** Reading a prologue is not counting the
reads, and `reads.py` takes one second.

### 15.2 The `u8` is not gated, and it is the one that seats

`reads.py` marks it `gated?`; the listing says otherwise - the branch at `0x1429d50d5` jumps
*to* the read and the fall-through reaches it as well [L]:

```
1429d50ac  r15d = [rbx+0x4080] ; [rbx+0x4080] = chairId      ; store it on the user
1429d50cd  [rbx+0x4098] = tick + second   (0 -> 1)
1429d50d3  test chairId, chairId
1429d50d5  jne  1429d50e5                 ; non-zero skips the clear
1429d50df  call [rax+0xc0]                ; zero -> CLEAR
1429d50e8  Decode1 -> al                  ; <- unconditional
1429d50ef  je   skip
1429d5100  call 0x141712040               ; CONSTRUCT the chair object
```

So the full body is **`u32 characterId, u32 chairId, u32 second, u8 show`** - 13 bytes - and
`show` is what actually builds the chair. A seat is `(id, 1)`, a release `(0, 0)`.

### 15.3 What was done

* `net::chair::user_sit_remote` now writes the byte, and a test asserts **13** with a comment
  saying that a length failing downward makes this a client-killer again.
* It was briefly disabled, and **that was the wrong call**. The owner: *"No, this is unacceptable.
  The chair appearance across different clients is an important part of the game."* They are
  right - the fault was the body, not the feature, and turning a requested feature off to
  avoid re-testing my own bug is not a trade that was mine to make. It is back on, on all
  three transitions.

### 15.4 What makes the re-enable different from the first attempt

Three checks, and **all three were missing when it killed a client**:

* the read count was redone **at depth 6**, so a read hidden behind a helper would have shown.
  It is still exactly three;
* `FUN_1429bb720`'s head reads exactly **one** `u32` before it dispatches, so the character id
  is not double-counted against the arm's two;
* a test asserts the body is **13** bytes and says in its own comment that a length failing
  downward makes this a client-killer again.

The remaining risk is honest and worth stating: the *lengths* are now measured, the *meanings*
of the second `u32` and of `show` are read off the listing, and **nothing has been on a second
screen yet**. If Tester2's client dies again the packet is still wrong - but it will be wrong
about a value, not about a size.

## 16. The relay works. Map chairs are a DIFFERENT mechanism, and the range is now exhausted

The owner, 2026-09-09: *"Tester 2 now sees Cobalt in a chair, and when Cobalt gets out of the chair,
that's correct too. Sitting in different chairs also reflects the correct chair model."*

So `0x02AD`'s body is right - all four fields, 13 bytes, and the chair id selects the model.
**And map chairs still do not work**, with the same packet carrying the seat index [L]:

```
05:42:10.611 <- 0x00DA 1800      seat 24
05:42:10.611 -> 0x02AD  character 213 on map seat 24, 13 bytes
05:42:11.553 <- 0x00DA 1900      the player moved to bench 25 and tried again
```

`0x02AD`'s field is a chair **item id** - it is handed to `FUN_141712040`, which builds a chair
object and renders its model. A seat index is not an item id, so there is nothing to draw.

### 16.1 The seat index has no packet, and that is now exhaustive rather than a failed search

The two halves of `IsSitting` are different state with different setters:

| | field | set by |
|---|---|---|
| Set Up chair | `+0x3c18`, an **object** | `0x02AD` -> `FUN_141712040` |
| map chair | `+0x3c28`, a **seat index** | `SetChair`, vtable slot 38 |

Everything that can set the seat index was enumerated rather than sampled:

* **`+0x3c28` has three writers** [L]: the `-1` initialiser `0x142769d49`, the `0x0224`
  decoder `0x1429ce827` (from body offset **416**), and `SetChair` itself.
* **`SetChair` is virtual-only** and is reached through `SetSeat` (slot 23, `+0xb8`).
* **The local dispatcher** `FUN_14289a3a0`: one chair arm in 218, and its only `SetSeat` call
  is the release.
* **The remote table**, all **15** arms - `0x293 0x2AA 0x2AD 0x2AE 0x2B0 0x2B1 0x2B2 0x2B3
  0x2B4 0x2B5 0x2B6 0x2B9 0x2BE 0x2C2 0x2C3`, everything else falling to the default
  `0x1415f0d70` - scanned for `SetSeat`, `SetChair` and direct `+0x3c28` writes: **none** [L].
* **`FUN_1429bafb0`** (`0x0226..0x0292`): none [L].

**So no packet in `0x0224..0x039F` sets a seat index.** The only paths are the user record
(`0x0224` body 416, for remote players) and `FUN_142d51930` - SetField - for the local one.

### 16.2 The one measurement that splits it, and it needs a seated attempt

That conclusion leaves two readings and they need opposite work:

* **the client seats itself and something else fails** - then `chairprobe` run *while trying a
  bench* shows `+0x3c18` non-null with flag 1, or `+0x3c28` at 24, and the bug is rendering or
  positioning rather than protocol;
* **the client changes nothing** - then it is still waiting, and since the whole opcode range
  is now excluded, what it waits for is not a user-pool packet at all. The next place to look
  would be SetField's own seat field, which is the only other thing that writes `+0x3c28`.

`tools/chairprobe.py`, run while sitting on a Henesys bench, answers it in one line.

## 17. MEASURED: the client does not seat itself on a map chair, and the range is now truly exhausted

`chairprobe` run **while a Henesys bench was being clicked**, with the vtable control passing
and the local-user global as the anchor [L]:

```
local CUser = *0x143aa8518 = 0x369d6018   (vtable OK)
  +0x3c28 chair id  = -1        <- unchanged
  +0x3c18 chair obj = 0x59047d8, flag = 0, checksum VALID
  -> IsSitting = FALSE
```

**Nothing changes.** The client sends `0x00DA(24)`, waits, and stays standing - so a map chair
is not client-side the way a Set Up chair is, and the reply is genuinely missing.

*(The object at `+0x3c18` has vtable `0x1433CECA0` here and `0x1433CEF78` when seated, so that
pointer is a base-class slot holding two concrete types - a "no chair" one and a chair.)*

### 17.1 A gap in §16's "exhausted", found and closed

§16 said the range was exhausted. It was not: the pool special-cases `0x0224` **and `0x0225`**
*before* the byte table, and only `0x0224` had been looked at. `0x0225` -> `FUN_1429ba980`
reads one `u32` and contains **no** `SetSeat`, `SetChair` or `+0x3c28` write [L]. The claim now
holds, but it did not when it was made.

### 17.2 What the seat actually is

Both of `FUN_142d51930`'s `SetSeat` calls pass a **`u16`** - `movzx edx, r14w` and
`movzx edx, word ptr [rsp+0x3c]` [L] - which matches `net::userpool`'s
`w.i16(-1); // 416 the seat index; -1 = not seated`. So the seat is the **`i16` at body offset
416 of a user record**, and the record is the only thing that carries it.

### 17.3 Where that leaves it

Every packet-driven writer of `+0x3c28` is now enumerated: the `-1` initialiser, the `0x0224`
record decoder, and `SetChair` via `SetSeat` - whose only packet callers are `FUN_142d51930`
and the `0x0318` release. **So the only thing that can seat the local player on a map chair is
a packet carrying a user record with field 416 set.**

That is a hypothesis with one obvious shape - send the player their own `0x0224` with the seat
index - and it is **deliberately not shipped**. `0x02AD` was shipped on a weaker hypothesis
tonight and killed Tester2's client, and `research/0x0224-remote-user-first-use-fault.md` is an
entire file about `0x0224` bodies faulting clients. The next attempt at this should be made on
a run where a second client is expendable, not on one where players are on the server.
