# THE CLIENT HAS ITS OWN COPY AND THE CLIENT WINS. The table lives at 0x143AC2400, 121 u64s,
# in the zero-initialised tail of `.data` - no bytes on disk, so no static read can produce
# it, and reading it that way once returned 120 confident wrong numbers that were actually
# exception-handling records. Every `-SetFieldProbe` run now dumps it from the running
# process on the positive-control watch's first hit; decode with
#   python tools/decode_dump.py --exp-curve
# and compare against this file. If they disagree, the dump is right and this is wrong: the
# client draws the EXP bar from its own copy, so a server that disagrees shows a bar that
# does not fill when it should.
#
# VERIFIED AGAINST THE CLIENT'S OWN TABLE, 2026-08-21. The comparison above had never been
# run. It has now been, against the dump in
# research/fixtures/equip-into-empty-hat-slot-kills-client-hook.log, and levels 1..99 agree
# EXACTLY - 99 of 99, zero disagreements. So these rows are no longer fan-sourced [I]; they
# are confirmed against the running client [L].
#
# Getting there needed a tool fix. `tools/decode_dump.py --exp-curve` labelled entry i as
# level i+1 - its comment claimed "Entry 0 is level 1's requirement" - so the first
# comparison reported all 98 levels disagreeing when none of them do. Entry **i** is level
# **i**'s requirement: [0] = 0 is the hole that makes the index 1-based, [1] = 15 is level 1,
# [119] = 28171993, and [120] = 0 because 120 is the cap and has no next level. 1 hole plus
# levels 1..120 is 121 entries with exactly 2 zeros, which is the 119 non-zero the dump
# reports. The same fix cleared a permanent false "monotonic: NO - suspect", which was the
# trailing cap zero being compared against the last real level.
#
# Levels 100..119 below come STRAIGHT FROM THAT DUMP rather than from the guide, which only
# went to 100. Level 120 is the cap: the client's own entry for it is 0.
