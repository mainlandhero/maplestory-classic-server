# Quest opening / closing scripts - the bodies the client does NOT ship.
#
# AUTHORED DATA, NOT GENERATED. Committed on purpose, like `data/shops.txt`. Nothing
# regenerates this file and `tools/dump_quests.py` must never write to it.
#
# ## Why this file exists
#
# Twelve of this client's 322 quests open with a *script* instead of a `Say` tree:
# `Quest.wz/QuestData/<id>.img/Check/0/startscript` names one (`q1002s`), `Check/1/endscript`
# names its closer (`q1002e`), and for all twelve the `Say."0"` node is **empty or absent**.
# The names are in the client. The bodies are not.
#
# That was settled by enumeration, not by search: every one of the 205 `.wz` archives under
# `client-patched/Data` was opened and all **10 021** images were decoded (0 errors), and the
# strings `q1002s` / `q1002e` occur **exactly twice in the whole tree** - as the two *names*
# inside `1002.img`. `Data/Etc/Script/Script.wz` exists and is a 63-byte header with **zero
# entries**; `Etc.wz/ScriptInfo.img` is the empty image `{}`; there is no `.js`, `.lua` or
# `.txt` anywhere under `client-patched/`. Full working and the named negatives:
# `research/quest-scripts.md`.
#
# So the script bodies were server-side in the original game and this project has to author
# them. The client's own GM command guide agrees: it ships `loadscript <file>`,
# `scriptrun <name>`, `runlua` / `loadlua` and `loadquest` - commands whose whole purpose is
# to make **the server** re-read script files.
#
# ## Format
#
# Deliberately the same four-column TSV as `gm-handbook/questlines.txt`:
#
#     questId <TAB> node <TAB> dotted.path <TAB> value
#
# because `world::config::load_quests` already parses exactly that, and a script quest needs
# nothing the WZ schema cannot express. These rows are an **overlay**: they are applied on
# top of the generated `questlines.txt`, and they only ever fill nodes the client left empty.
# They must never contradict a row the client ships - if one does, the client's row wins and
# this file has a bug.
#
#   Say  0.<n>       the opening conversation, in line order. The LAST line goes out as the
#                    quest-flavoured yes/no box (message type 0x10) when a `0.yes` exists.
#   Say  0.yes.<n>   what the NPC says after Accept. Sending this is what "the quest started".
#   Say  0.no.<n>    after Decline.
#   Say  1.<n>       the closing conversation, driven by the `endscript`.
#   Act  0.item.<n>.id / .count     what accepting hands over. A script quest's `Act."0"` is
#                                   EMPTY in the WZ - the apple came from the script.
#   Act  1.exp                      what completing pays.
#
# ## Provenance of every line below
#
# Where a line is quoted from the client it is marked; where it is written by us it says so.
# This matters because a line that came out of `String.wz` is evidence and a line we wrote is
# a placeholder that the owner may want to replace. No attempt is made to reconstruct Nexon's
# original wording - that is not recoverable from anything on this machine.

# **The first job advancement has no quest at all.** All 322 quests were enumerated and
# there is no `Act.<n>.job` key anywhere in the tree, so no quest in this client can change
# a job even in principle. It is an NPC script, and NPC scripts are server-side - the same
# finding as `q1002s`, one level up. `research/job-advancement.md` has the enumeration, its
# positive controls, and what to build instead.
#
# ## What these four rows are, and what they are NOT
#
# Each of these quests has a **client-side opening** (`Say."0"` is shipped, so the client
# sends action 1) and a **scripted close** (`Check.1.endscript = q<id>e`, so the client sends
# action 5). Only the `Say."1"` half is missing, which is why they are cheap.
#
# **No job change is attached to them, deliberately.** `Act."1"` for all four carries
# `exp 3150` and nothing else [L], there is no `Act.<n>.job` key in the schema to hang one
# on, and the second-job table (110/111/112, 120/121/122, ...) does not exist in this server.
# Adding a line of dialogue is honest; making these rows silently promote a character would
# be a job change with no table behind it. So on completing one of these today the player
# gets the line, the EXP and the journal row, and stays whatever job they were.
#
# ## Provenance: all four lines are OURS
#
# Stated plainly rather than hedged. `String.wz/Npc.img` gives 511 / 313 / 221 / 411 four to
# six lines each and every one of them is an idle line - Dances with Balrog's complete
# repertoire is `d0`, `d1`, `idle0`, `idle1`, `info0`, `info1`, and `d0` = `d1` = *"Those who
# want to become a warrior, come see me..."*. [L] There is **no closing dialogue for these
# quests anywhere in the client**, in either the English tree or the Spanish overlay.

# The client does carry `QuestInfo.2` for each - *"#b#p511##k in #b#m10004000##k welcomed me
# warmly, and I gained a new job..."* [L] - but that is the **player's journal voice**, not

#
